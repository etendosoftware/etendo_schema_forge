# Profit & Loss

## Intent
Show the result of a period (revenue, expenses and the profit or loss they add up to) as the indented account-report tree Etendo Classic prints (`c_acct_rpt`, report type `N`), for one accounting schema and organization, optionally compared with a reference period.

## What this report should allow
- Browse the report from the Finance / Reports menu listed as **Pérdidas y Ganancias** (es) / **Profit & Loss** (en).
- Pick an Accounting Schema (General Ledger), a Year or a date range, and optionally a comparison year or date range.
- Filter by one or more business partners (**Contacto**) and products (**Producto**) in the **Dimensiones** section (ETP-6080). Both are optional multi-select popups; empty means no filter. The product picker uses the `product-all` selector (any active product of the role's organizations, services included), not `product`, which only lists products with stock (ETP-6080).
- Choose the account level (Heading / Account / Breakdown / Subaccount) and whether to show only accounts with value.
- Render the report inline as HTML preview and download it as PDF, XLSX, or CSV. XLSX and CSV share the Balance Sheet's flat grid (see `balance-sheet.md`).
- With the `dynamic-reports` flag on, the report's card (and list row) in *Informes* carries a sparkle mark (top-right corner of the card; tooltip *Interactivo: …*) and a soft primary glow (`DynamicReportBadge.jsx`; only reports in `DYNAMIC_REPORT_IDS`). Use the interactive view instead: live filters, an on-screen tree, comparison, splits by dimension and a drill-down to the ledger, the entry and the document (see *Interactive view* below).

## Interaction model
- Route: `/report-viewer?report=profit-loss`. The old viewer also reads parameters from the URL (`&dateFrom=…`) and runs the report; the interactive view reads and writes its own selections in the URL (see *Selections in the URL* below and `docs/dynamic-reports.md`).
- No ← back button in the TopBar breadcrumb (ETP-5519); the in-page **Cancelar** button (`action-cancel`) returns to the report catalog.
- Visibility: Finance / Reports menu, category `finance`.
- Implementation type: contract-driven SQL report (`artifacts/profit-loss/report-contract.json`). The SQL returns the flat node list; `buildAccountReportTree` (core `report-grouping.js`) builds the tree, the roll-up and the formula nodes.
- Layout: grouped listing, **landscape** orientation (`"orientation": "landscape"` in the contract), always and outside the `dynamic-reports` flag (ETP-6239). Until then every PDF of this report came out portrait: `templates/reports/base.css` forced `@page { size: A4 portrait }`, which overrode the contract's `orientation` in both render engines. That line is gone, so the **other landscape reports** (Libro Mayor, Diario, Sumas y Saldos, Impuestos, the two aging reports, stock and not-shipped orders) are now truly landscape too, with base.css's 15 mm margins. The `print-*` printables set their own portrait `@page` and are unaffected.

## Reactive behavior and dependencies
- The report does not auto-render: the user presses **Run Report** after picking parameters (old viewer; the interactive view applies every change on its own).
- `acctSchemaId` and `orgId` are required, hidden and defaulted. `yearId` is required in this viewer and depends on `orgId`.
- The year and the date range combine: the year clamps activity to its periods, and `dateFrom` / `dateTo` narrow it further. The SQL accepts a request with dates and **no** `yearId` (ETP-6080, for the interactive view): the year clause is optional, so it is stripped instead of zeroing every amount.
- With **Compare To**, `referenceYearId` becomes required and the reference columns are computed the same way.
- Amounts are raw debit − credit in SQL; each branch's sign is applied in JS. Organization scope uses `ad_isorgincluded`, so a parent org includes its children. General Ledger and Journal Entries use the same rule, so a ledger drilled from a parent-org row adds up to its amount; they resolve the org tree once over `ad_org` (`fa.ad_org_id IN (SELECT … ad_isorgincluded(o.ad_org_id, …))`) instead of once per line, with identical results. Their account filter (`fromAccountId` / `toAccountId`) compares account **codes** (`ev.value`), so a drill-down passes the row's `value`, not its id. A role that cannot read the requested org gets `403 ORG_ACCESS_DENIED` (ETP-6080).
- The contract declares `"trend": "result"`: with a comparison, each row carries `variationAmount`, `variationPct` and `trend` (`improves` when the result goes up: revenue up or expense down).
- With a comparison, PDF, XLSX and CSV add **Variation** and **Variation %** after the reference amount (ETP-6080). The % cell is empty when the reference amount is 0. Excel/CSV variation values are rounded to 2 decimals and a null % is an empty string cell, never an empty number cell (html-to-xlsx writes NaN there and the file does not open); this includes the period-columns layout (`round2`/`numCellType` in the report's `helpers.js`). The XLSX/CSV templates are shared byte-for-byte with Balance Sheet and print these columns only when the contract declares `labels.variationAmount`, so Balance Sheet exports are unchanged.

### Interactive view (ETP-6080, flag `dynamic-reports`)
With the flag on, the report opens `components/reports/dynamic/DynamicReportView.jsx` instead of the old viewer. There is no **Generar informe**: every change in **Personalizar informe** sends a new query (`POST /api/reports/profit-loss/query`, 300 ms after the last change, an older request cancelled).
- **Opening period:** the fiscal year that contains today, from its first day to today (a July calendar opens on 01/07). The years come from the year selector with `selectedOrgId`, so they are the calendar the org really uses. No year contains today, or the org has no calendar: 1 January to today, with a hint. The query never sends `yearId` / `referenceYearId`: the year picker and the **Año** shortcut only fill the dates. A closed year picked by hand fills its whole range; the current one stops at today. The year selector shows the year the period exactly covers (the opening period and **Año** show the current one); a period that is not a whole year, such as **Mes**, leaves it on *Seleccionar…*.
- **Shortcuts:** Mes, Trimestre (to date), Año (fiscal year to date). There is no rolling 12-month shortcut: it would cut across two fiscal years, and the dates can still be set by hand.
- **Filters:** Contacto and Producto (multi-select, the old viewer's picker). Organización only when the role reaches more than one org (`*` not counted).
- **Tree:** the query returns every level and the screen folds it. The level selector (default from the contract, Cuenta), **Expandir todo** and **Contraer todo** set the base; then rows open and close one by one. The base applies to every result, so a row a new filter brings in follows it instead of showing folded; the user's own opens and closes are kept. Folding sends no request.
- **Comparison:** Mismo período del año anterior or Período anterior. Adds Comparado / Var. / Var. % columns, green when the result improves and red when it worsens (`trend`). Both compared ranges travel in every request, so switching the comparison on, off or between the two sends **no request** in any Columnas mode. The exact ranges are in *Comparison ranges* below.
- **Columnas:** Total (the default, one amount column), Por mes or Por trimestre (one group of columns per calendar month or quarter). See *Columns by period* below.
- **Headline figures (`DynamicReportKpis.jsx`, reports in `RESULT_REPORT_IDS`):** four cards above the tree — **Ingresos** (the income accounts, PGC group 7), **Gastos** (the expense accounts, group 6, as a positive figure; a refund on an expense account lowers it instead of counting as income), **Resultado del ejercicio** (their difference; a lime edge when positive, a red one when negative) and **Margen** (Resultado del ejercicio ÷ Ingresos × 100: the profit left from every 100 of income). Each card has an ⓘ whose tooltip explains the calculation. The figures add the first account level under each line, so subaccounts and formula subtotals never count twice; a line with no accounts listed (or an account outside groups 6/7) goes by its own sign. With a comparison each card shows a ▲/▼ pill with the change (in points for the margin) and the compared value; the pill is green when the change is good news, so Gastos going up is red. Pure helpers: `reportVisuals.js`.
- **Headline cards in the PDF (ETP-6239):** the interactive view's PDF opens with the same four cards in one row (landscape A4): value, and with a comparison the ▲/▼ pill (red worse / green better, `pp` for Margen) plus *vs <compared value>*. The view sends the very figures on screen as the `kpis` render param (JSON of `kpiCards()` in `reportVisuals.js`, the same function the screen cards use; only the PDF carries it), and `template.hbs` formats them with the canonical `formatCurrency` helper after `parseJson`. No `kpis` (the old viewer, Excel, CSV) means no cards.
- **Look of the tree:** kept quiet on purpose: a muted header row; each top-level line gets a thin primary edge on the left; formula subtotals (*A. RESULTADO DE EXPLOTACIÓN*…) a muted fill, a rule above and a thin lime edge. Every amount carries a thin bar with its weight within its parent (a top-level line: within the largest top-level line; a split part: within the parts' total), soft primary for positive amounts and soft lavender for negative ones; formulas have none. The compared column is muted, and Var. % is a ▲/▼ pill coloured by `trend`.
- **Split:** **Desglosar cuentas por** Organización / Contacto / Producto (Organización, and the organization chip under the title, only when the role reaches more than one org, like the org picker; a link restored with `splitBy=org` for a single-org role opens without a split) adds a toggle on every leaf account that lists its parts (`splitQuery`). Postings with no contact or product show as *(sin asignar)*.
- **Context line:** period, organization, filters, Columnas, comparison and split as chips. Everything can be removed from its chip except the **organization**: the query requires one, so it is changed in the panel, never cleared. The chips stay on screen when the panel is collapsed, so they are the active filters then.
- **Exports:** PDF / Excel / CSV render the same params plus `accountLevel` and `expandedNodeIds`, so the file shows the rows the screen shows. With Mes/Trimestre they also send `columns`, `periods`, `hiddenCount` and `compareMode` (see *Columns by period*).
- **Errors:** a role without access to the org sees *No tienes acceso a esta organización* and keeps the last result; a role without access to the report itself, *No tienes acceso a este informe*; any other failure, *No se pudo cargar el informe*. The old viewer (flag off) shows the same translated messages when `/render` is refused with `ORG_ACCESS_DENIED` or `REPORT_ACCESS_DENIED`; other render failures keep the server's message.
- **Report access:** `/render` and `/query` check that the role can open the report (any tier in the Roles matrix), before the org check and before any SQL. The source is NEO `myreportaccess`: `governed` lists the 9 catalog reports, `reportAccess` the ones the role can open; a report outside `governed` (printables, reports open by design) is not checked. The drill-down only offers the steps the role can open: without General Ledger the account name is plain text; without Journal Entries the ledger lines do not open an entry. A backend that does not send `governed` yet is not enforced (deploy skew; see `assertReportAccess` in core).
- **Drill-down (side panel):** a leaf account's name opens its ledger (`POST /api/reports/report-general-ledger/query` with the view's period, org, schema, Contacto and Producto, and the account **code** as `fromAccountId` = `toAccountId`, plus its id as the hidden `accountId`, so the SQL reads `fact_acct` through the account index instead of the client's whole history — production opening balance 21–23 → 6–7 ms): opening, debit, credit and closing balance (debit − credit, the closing includes every earlier period), plus **Movimiento del período**: the period's debit − credit signed like the report row, so it equals the amount clicked; and a text search over the loaded lines. The ledger loads at most 500 lines (`LEDGER_LINE_CAP`; production, Nov 2026: p99 324 and max 661 lines per account and year). Past the cap only the opening balance is shown, since debit, credit, closing and movement summed over part of the lines would be wrong, with a note and **Cargar todas las líneas (puede tardar)**, which reloads without the limit. A summary account only folds. The ledger and the entry are requested right away when clicked (`debounceMs: 0`); only filter changes wait 300 ms. A line opens its whole entry (`report-journal-entries` with only `acctSchemaId`, `orgId` and `factAcctGroupId`, so no line is filtered out and a restricted role is not refused), with the account you came from highlighted, and **Abrir documento** opens the document in a new tab. An entry whose table has no window mapped ends there with a note. The breadcrumb (report › account › entry) goes back a step. The document URL is built by `components/reports/reportDocumentUrl.js`, shared with the old viewer's `navigate-invoice` message.
- **Opened from the Balance Sheet (ETP-6083):** the 129 result panel of the balance sheet links here (`/report-viewer?report=profit-loss&dateFrom=<fiscal-year start>&dateTo=<Hasta>&orgId=…`, with its contact / product filters), using the URL keys below. P&L behaviour is unchanged by ETP-6083.
- **Dates from `/query`:** `pg` sends a SQL `date` as the server's local midnight in UTC, so the panel reads the day with `sqlDateDay` (rounded to the nearest UTC day), never the raw prefix.
- **Telemetry:** `report_opened`, `report_filter_applied`, `report_group_toggled`, `report_drilldown` and `report_panel_toggled`, one `reportSessionId` per report session. Firing rules: `docs/ops/app-shell-observability.md` → *Interactive report events*.

#### Selections in the URL (ETP-6239, flag `dynamic-reports`)
The interactive view keeps its selections in the URL (F5, bookmarks and shared links restore them). This is an engine feature shared by every dynamic report: see `docs/dynamic-reports.md` → *Selections in the URL*. For this report the owned keys are `orgId`, `dateFrom` + `dateTo`, `columns`, `compare`, `splitBy`, `bPartnerId` and `productId`.

#### Comparison ranges (ETP-6239)
Pure helpers in `dynamicDates.js`; the server never derives a range, it only validates the ones the client sends.
- **Same period last year** (`minusOneYear`): the bounds move back one calendar year, and **the last day of February maps to the last day of February**: 28 Feb 2021 → 29 Feb 2020, 29 Feb 2024 → 28 Feb 2023. Any other day keeps its day number. **Behaviour change, in Total mode too**: until ETP-6239 the rule was "29 February → 28", so a range ending on 28 Feb of the year after a leap year compared against a range that lost the postings dated 29 Feb (Jan–Feb 2021 against Jan–28 Feb 2020 mismatched 8 of 11 accounts on a local database). Total mode, the buckets and the single-period reports now agree.
- **Previous period, Total mode:** unchanged: the same number of days, ending the day before the range starts (`previousPeriod`).
- **Previous period, Mes/Trimestre (D3):** each bucket compares with the **previous calendar month or quarter**, keeping its days shifted back 1 or 3 months. The day is clamped to the target month's length, and a day that is the last of its month stays the last of the target month, so `from <= to` always holds: 15-31 Mar → 15-28 Feb; 30-31 Mar → 28-28 Feb; a partial Q2 15 Apr-30 Jun → 15 Jan-31 Mar.
- **The Total column's compared range is one range in period mode:** `[prev(first bucket).from, prev(last bucket).to]`. The buckets are contiguous, so it equals the sum of the buckets' compared ranges, and the drill-down has a real range to open.

#### Columns by period (ETP-6239, flag `dynamic-reports`)
- **Columnas** (panel, *Comparación* section): `total`, `month`, `quarter`. The buckets are the **calendar** months or quarters inside `[dateFrom, dateTo]`, clipped to it. A bucket that does not cover its whole month or quarter is **partial** and its header carries `*`, with the note *\* Mes o trimestre incompleto dentro del rango elegido*. Headers are short (`sep 26`, `T3 26` in Spanish, `Q3 26` in English): `formatCalendarMonthShort` / `formatCalendarQuarterShort` on screen and the `periodLabel` helper in the exports, from the same fixed month table (Intl would give "sept"). The range total (bucket 0) is the **last** group, labelled *Total*.
- **What Comparado is compared against:** under *Comparado* the screen table and the PDF print a small muted `(ene 25)`; Excel and CSV put it in the same header cell, `ene 26 Comparado (ene 25)` (CSV through `csvField`). A Mes / Trimestre group names the compared bucket (`ene 25`, `T1 25` / `Q1 25`; "Mismo período del año anterior" is the same month or quarter a year back, "Período anterior" the previous calendar month or quarter). The Total group, and every group in Total mode, name the compared dates (`dd/mm/yyyy – dd/mm/yyyy` in Spanish, `mm/dd/yyyy` in English: the comparison chip's range). On screen it is `comparedLabel` of `columnModel` (`formatCalendarMonthShort` / `formatCalendarQuarterShort` / `formatCalendarDate`); in the exports the canonical `periodCompared` / `periodComparedHeader` helpers read it from the same `periods` request param the engine was asked with, so both show the same range. Balance Sheet shares the Excel / CSV files and never sends `periods`, so its output is unchanged.
- **What is shown:** the screen and the PDF show the **last 12 months or 8 quarters** plus the Total **without a comparison**, and the **last 6 months or 4 quarters** with one (a comparison takes 4 columns per period, so fewer fit the same width). The limits are core's `SCREEN_PERIODS` (`report-periods.js`), read through `periodLimit` (`reportColumns.js`), used by the screen, the PDF request and the note. The query always asks for the larger set, so turning the comparison on or off trims or restores the columns and the note on screen with **no new request**; the PDF asks for the set of its own mode. A note *No se muestran N períodos anteriores. Excel y CSV incluyen todos los períodos.* counts what the current mode leaves out (the request's `hiddenCount` plus what the comparison trims); for exactly one it reads *No se muestra 1 período anterior…* (`dynamicReportHiddenPeriodsOne`, and the PDF's equivalent). Excel and CSV print **every** period. Row visibility follows the same limit: core computes `visible.sly` / `visible.prev` of the `/query` answer only over the range total and the last 6 months / 4 quarters (`comparedPeriods`, from `SCREEN_PERIODS` in core `report-periods.js`, the single source; `reportColumns.js` re-exports it from the core package, so there is no copy), while `visible.none` looks at every requested period. So a row never shows in comparison mode with every visible column empty (the Total always counts, so only a row that nets to zero over the range and moves only in a trimmed month is hidden). A render (PDF, Excel, CSV) passes no limit: the PDF asks for just the shown periods, and Excel / CSV print every period, so their rows match a fresh report over all of them.
- **Groups of columns:** each group is *Importe* alone, or with a comparison *Importe / Comparado / Var. / Var. %* (`columnModel` in `reportColumns.js`). The table scrolls horizontally with Concepto sticky on the left (opaque background on every row state), two header rows (`scope="colgroup"` / `scope="col"`). A tall table keeps a proxy horizontal scrollbar pinned to the viewport bottom (`StickyHScroll`, screen only; see `docs/dynamic-reports.md` -> *Horizontal scroll*).
- **Same rows as a fresh report:** core answers `visible` and `parentIds` for each comparison mode (`none`, `sly`, `prev`), so the comparison toggle only picks which set to show (`rowsForMode`) and the rows are the ones a new request would have returned. A row is visible in a mode when one of its cells for that mode is non-zero or it is *always shown*.
- **Split:** an open split has a value in every period, in every mode (`splitPeriodQuery`), so it survives a comparison or Columnas switch.
- **Drill-down:** a current cell opens the ledger for **its bucket**; a *Comparado* cell for **its compared range** (for the Total column, the single range above). *Var. €* and *Var. %* cells are not clickable.
- **KPI cards** read bucket 0 of the chosen mode; the comparison chip shows the range actually compared.
- **Excel / CSV limits (D5):** at most **24 months or 8 quarters** (25 buckets, Total included), and the range may not run past `dateFrom` + 24 months, in any Columnas mode, Total included. Above it the server answers `400 PERIOD_RANGE_TOO_LONG`; the view disables Excel and CSV beforehand with *Excel y CSV admiten hasta 24 meses u 8 trimestres. Acorta el período para exportarlos.* and shows the translated `reportErrorPeriodRangeTooLong` if the server still refuses. The cap applies **only** to Excel/CSV: a long range works on screen and in the PDF. An invalid `periods` shows `reportErrorInvalidPeriods`.
- **PDF:** always landscape (see *Interaction model*). **With a comparison, 2 groups per page** (the Total counts as a group), 8 pt, Concepto fixed at 45 mm; Concepto and the two header rows repeat on every page (`meta.columnPages`, `periodPages` helper, `page-break-before` between tables, explicit `table-layout: fixed` and `<colgroup>`; without them Chrome shrinks the table and cuts columns). **Without a comparison, the groups go in even pages of at most 7** (12 months + Total = 7 + 6; 8 quarters + Total = 5 + 4): measured on A4 landscape (267 mm of content), 13 groups on one page leave 17 mm per column, and an amount like `-1.234.567,89` needs 20.5 mm at 8 pt (18 mm even at 7 pt with tight padding), so it would overflow; at 7 groups a column is 31.7 mm. Done by `periodPages`, which caps the page size at 7 whatever the engine's `columnPageSize`. Account rows use 1 mm vertical padding (`.period-table tbody .tree-row td`) so the closing row does not spill alone onto a page after the headline cards. **Known limit:** whether the last row ends up alone still depends on the row count, the filters and the branding height; it is not guaranteed, and a recurrence gets its own ticket, not more padding tweaks. The hidden-periods and partial notes close the report.
- **Excel / CSV:** the same flat grid as before with one amount group per bucket (every bucket, Total last, headers through `csvField`); with a comparison each bucket adds Compared, Var. and Var. %. The templates are byte-for-byte shared with `balance-sheet/`, which never sends `periods`, so its loops come out empty and its exports are unchanged.
- **Collapsible panel (D8):** *Personalizar informe* collapses to a `w-10` strip on desktop and to a bar across the top on mobile (the strip carries a badge with the number of removable active filters, `aria-expanded`, `aria-controls`). A manual toggle is **remembered per username** (`etendo.reports.panel.collapsed:<username>`, `useReportPanelCollapsed`, every storage access guarded). Choosing Mes or Trimestre **collapses it automatically, for the session only** (nothing is stored); focus then moves to the expand button, since the focused select disappears.
- **Reversed dates:** a *Desde* after *Hasta* sends no query, no split and no export: the view shows *La fecha "Desde" es posterior a la fecha "Hasta"* (`dynamicReportErrorReversedDates`), clears the previous result and disables the export buttons and hides the split toggle.
- **Telemetry:** `report_panel_toggled` (`panelState` `collapsed`/`expanded`, `trigger` `user`/`auto_columns`; the property is `panelState` because the payload policy denylists `state`) and `report_filter_applied` with `type: columns` (timed like the other filters). The comparison toggle emits `report_filter_applied { type: comparison }` **directly, with no `durationMs`**: it sends no request, so there is nothing to time and it does not go through `markFilter`. Rules: `docs/ops/app-shell-observability.md` → *Interactive report events*.
- **Flag:** the view, the columns and the panel are behind `dynamic-reports` (registry entry `flags-registry.json`; `make flag-debt FLAG=dynamic-reports`). **Not behind it:** the landscape PDF fix, the `orientation` in the contract, and the new core/engine code, which is inert without `periods`.
- **ShowValueCond P/N:** a clamped month may not add up to the clamped total, so a *P/N* summary node can show a different value in a month than the sum of its months. Each column equals the report generated for that range. Today every P/N node of the local chart belongs to balance accounts (5xx), not to the P&L, so it matters for the Balance Sheet follow-up (ETP-6292), not here.
- **Out of scope:** Balance Sheet by period (ETP-6292, blocked by ETP-6083), Sumas y Saldos by period (ETP-6293, blocked by ETP-6084), and columns by period over MCP (`ProfitLossReportHandler`, whose sums must stay mirrored by hand with `sql.query`; `periodQuery` is added next to it, never in place of it).

### The `/query` route (ETP-6080)
`POST /api/reports/:id/query` answers JSON instead of a document. It is served by the same `report-server` as `/render` (CloudFront sends every `/api/reports/*` request there; in `make dev`, the Vite plugin `report-api.js`), and runs the same session and org check before any SQL. The handler is core's `cli/src/report-query.js`, shared by both engines.
- **Request:** `{ params, locale, limit? }`. `params` are the contract's parameters, the same values `/render` takes. A JSON `null` body reads as `{}`.
- **Account-tree report** (a contract with `sql.operandsQuery`, like this one): `{ kind: 'tree', rows }`, every level at once (the view folds them; `accountLevel` is ignored). Each row: `node_id`, `value`, `name`, `elementlevel`, `parentId`, `sign`, `isFormula`, `amount`, `amount_ref`, and with `compareTo: 'true'` the variation fields above.
- **Same, with `periods` (ETP-6239):** `{ kind: 'tree', rows, periods, hiddenCount }`, **in every Columnas mode, Total included** (Total has one period). `periods` is `[{ idx, dateFrom, dateTo, partial }]`, `idx` 0 being the range total. Each row adds `cells[]` (index = position in `periods`): `{ amount, sly: { amount, variationAmount, variationPct, trend }, prev: { … } }`, plus `visible: { none, sly, prev }` and `parentIds: { none, sly, prev }` (the nearest ancestor visible in that mode; `parentId` stays the unfiltered one). The top-level `amount`, `amount_ref` and variation fields are bucket 0's current and same-period-last-year values. In this shape `compareTo` and the reference dates are not sent: the comparison is read from `cells[].sly` / `cells[].prev`.
- **Split** (`splitBy` + `splitNodeId` + `splitSign`): `{ kind: 'split', rows }`, one row per dimension value (`node_id` = its id, `null` = unassigned), signed like the account. With `periods`: `{ kind: 'split', rows, periods, hiddenCount }`, each row with `cells[]` like a tree row, in every mode.
- **Listing report** (General Ledger, Journal Entries): `{ kind: 'rows', rows, openingRows }`, the SQL rows as they come. A SQL `date` arrives as a UTC timestamp (see *Dates from `/query`*).
- **Errors:** JSON `{ error, code }`. `401` no session, `403` no CSRF, `REPORT_ACCESS_DENIED` or `ORG_ACCESS_DENIED` (no SQL runs), `502 REPORT_ACCESS_UNAVAILABLE` (the access check could not be read), `404 REPORT_NOT_FOUND`, `400 QUERY_NOT_SUPPORTED` (not a SQL report), `400 INVALID_LIMIT`, `400 SPLIT_NOT_SUPPORTED`, `400 INVALID_PERIODS` and `400 PERIOD_RANGE_TOO_LONG` (ETP-6239, also answered by `/render`), `500 QUERY_FAILED` (logged server-side; the SQL and the DB message never reach the client).

### Interactive-view parameters (ETP-6080)
Declared `hidden: true`, so they never appear in the filter panel or as an active filter in the PDF header:
- `expandedNodeIds`: comma-separated ids of the expanded rows. When sent, the export prints exactly those rows instead of cutting at the account level. `none` means no row is open (only the top rows print). A blank value counts as not sent: the old viewer sends `''` for every parameter it has no value for, so it keeps the account-level cutoff.
- `splitBy` (`org` / `bpartner` / `product`), `splitNodeId`, `splitSign`: split one account (and its whole subtree) by a dimension through `sql.splitQuery`, which reads `fact_acct` with exactly the main query's period, organization, schema and dimension predicates, so the parts add up to the account's amount.

Sent by the interactive view (ETP-6239) and **not declared in the contract**, on purpose: a declared parameter is pasted raw into the SQL by `applyPlaceholders`, and `periods` is built by the engine from validated dates (core `docs/report-query.md`):
- `columns`: `total` (default), `month` or `quarter`.
- `periods`: `from..to|slyFrom..slyTo|prevFrom..prevTo` tuples joined by commas, **bucket 0 (the range) first**, every date `yyyy-MM-dd`. Present, it switches the report to `sql.periodQuery` / `sql.splitPeriodQuery`; absent or `''` (the old viewer), nothing changes.
- `hiddenCount`: how many earlier periods the screen or PDF left out (echoed back for the note; integer 0-1000).
- `compareMode` (exports only): `none`, `sly` or `prev`, which rows and columns the file prints. An unknown value counts as `none`.

Caps (`400`): **screen and PDF** take up to 13 buckets (the range plus 12 months or 8 quarters; `SCREEN_MAX_BUCKETS` in core `report-periods.js`); **Excel and CSV** up to 25 and a range up to `dateFrom` + 24 months, compared ranges included (`PERIOD_RANGE_TOO_LONG`). A month bucket is at most 31 days and a quarter 92. Everything else malformed is `INVALID_PERIODS`: bad shape or day, `from > to`, a period outside the range, a compared range too far from its period, a parameter carrying `__PERIODS__`.

### Performance (ETP-6080, measured 2026-11-04)
Production read replica, the client with the most accounting lines (9.2k lines in its main schema, 6 orgs), org `*` (every org), a three-year period. Server execution time (`EXPLAIN ANALYZE`, 3 runs each); the browser adds the network round trip on top:
- Tree: 140–190 ms (98 rows); with a comparison, the same.
- Split by contact, product or organization: 22–30 ms.
- Operands query: 2–4 ms.

Those numbers predate the 2026-11-05 rewrite. Before it, almost all of the tree's time was the scan of every `fact_acct` line the client ever posted, with `ad_isorgincluded` evaluated on each (about 14 µs per line): the period lived only inside the sums, so the cost followed the client's history, not the period. The tree and split queries now (1) resolve the org tree once over `ad_org` (`fa.ad_org_id IN (SELECT … FROM ad_org …)`, as General Ledger and Journal Entries do) and (2) keep in the `WHERE` only the lines that can fall in the current period or, when comparing, the compared one, written as blank-strippable clauses (`AND ('__DATEFROM__' = '' OR … OR (<compared period>))`) so a blank date, year or reference date opens that side instead of leaving a placeholder. The `SUM(CASE …)` still decides which period a line counts in, so the answer is unchanged: checked identical on 12 parameter combinations (dates, years, both, open compared period, all orgs, a contact filter) for the tree and the split. Guarded in `report-profit-loss-account-tree.test.js`. Production, measured 2026-11-05 on the read replica: same client as above (11.6k lines over 2019–2021, the largest on the instance; the rest have under 1k), all orgs, server execution time (`EXPLAIN ANALYZE`, 3 runs). Old vs new SQL returned identical rows for the tree and the split in every case.

| Period | Before | After |
|---|---|---|
| 3 years | 141–187 ms | 22–28 ms |
| 1 year | 134–153 ms | 7–8 ms |
| 1 year vs the previous one | 136–225 ms | 14–19 ms |
| 1 month | 136–387 ms | 4 ms |

A second pass (independent review, same day) found two gaps in that claim and fixed them: (1) estimated at about one row, the facts aggregate could be re-run once per tree node (production, year only: 62 → 8.7 ms), so the CTE is now `facts AS MATERIALIZED`; (2) with a comparison, the OR-shaped bounds could not use the date index and read the schema's whole history, so a single range covering both periods (`LEAST`/`GREATEST`, strippable) was added to the tree and the split (production, a month vs the same month last year: 11.5 → 4.7 ms). Identical rows on local (12 combinations) and production (6 periods, tree and split). What still grows with the number of tenants: `fact_acct` has no index scoped by schema/client and date, so a period scan also reads other tenants' lines in that period; tracked as a separate ticket. Over the SSM tunnel every query took about 265 ms either way: that is the round trip, not the query. The data is still small (few clients, little history), so these figures show the shape of the gain, not a load limit.
