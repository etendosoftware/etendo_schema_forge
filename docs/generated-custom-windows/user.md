# User

## Intent
This window should let administrators maintain a person’s application identity, review basic security state, define default working context, and assign the roles that control what the user can do in the system.

## What this window should allow
Users should be able to:
- create, find, open, update, and delete user records;
- maintain identity fields such as Name, First Name, Last Name, Email, Description, Position, and Phone;
- connect the user to a Business Partner and Supervisor through search-based selectors;
- set or update the Password while reviewing read-only security indicators such as Expired Password, Locked, and Last Password Update;
- choose default context values for Language, Client, Organization, and Warehouse;
- assign 1+ system-level template roles (Finance/Sales/Purchasing/Inventory) to an existing user via a multi-select chip control in the header, see a live per-role permission-preview matrix in a dedicated "Roles del usuario" tab before saving, and read/filter each user's applied roles as chips from the Users list grid (ETP-4906, superseding the single-role picker from ETP-4512).

**Role assignment — multi-role composition (ETP-4906).** `AssignTemplateRolesControl` (`tools/app-shell/src/windows/custom/user/AssignTemplateRolesControl.jsx`, wired as `window.headerExtra.customForm`) replaces the old single-select `AssignRoleControl`. It renders the user's currently-selected template roles as removable chips (+N overflow when collapsed) with a checkbox list to add/remove roles, sourced from `fetchTemplateRoles()` (`SFSystemRoleTemplates`) — the 4 fixed system-level template roles (no `isClientAdmin` filter needed: that endpoint never returns a client-admin row at all, there being no such role at system level). **DEV wave 7 repointed this from the original `SFRolesOverview`-backed catalog** — `fetchRolesOverview()`/`SFRolesOverview` is still used elsewhere on this window (the grid's `activeWindowIds` window-exposure filter and `RoleChipsCell`'s admin-detection branch, see below), but no longer supplies the role/column catalog itself. Selection is **local-only until Guardar** — toggling a chip never calls `onChange('defaultRole', ...)` or fires any network request; it only mutates a shared selection held in React Context (`roleSelectionContext.js`, `useRoleSelection()`), consumed by the sibling "Roles del usuario" tab below for its live preview. `defaultRole` itself stays a read-only field on the detail form (unaffected by this control), and the control renders a save-first placeholder for a not-yet-persisted user (composition requires an `AD_User_ID` — never attempted on create). On Guardar, `windows/custom/user/index.jsx` (the window's custom wrapper, registered as `customLoaders['user']` in `tools/app-shell/src/windows/registry.js`) diffs the local selection against the set it fetched on load (`fetchUserRoleAssignments(userId)`, `tools/app-shell/src/lib/userRoleAssignmentsApi.js`) and, only if it actually changed, calls `saveUserRoleAssignments(userId, templateRoleIds)` — a thin wrapper around the existing `SFAssignUserRoles` webhook, which fires exactly once with the FULL desired set (a set-reconciliation call, not additive). On the backend, `SFAssignUserRoles`/`UserRoleCompositionService` (`com.etendoerp.go`) resolve or create the user's personal composition role and reconcile its `AD_Role_Inheritance` rows against the desired template ids — the same most-permissive-wins composition model ETP-4852 already built, unrelated to the legacy `AD_User_Roles`/`Default_Ad_Role_ID` single-row sync ETP-4512 introduced.

**Admin-initiated user creation (ETP-4829):** Email is now a mandatory field (`required: true` in `decisions.json`/the contract) on both create and edit. Username is no longer shown on this window at all — `decisions.json`'s `username` field is `visibility: "system"` (excluded from the generated frontend contract entirely, confirmed absent from `UserForm.jsx`/`UserTable.jsx`/`mockData.js`) and is always a direct, lower-cased copy of Email, matching the convention `EtendoGoJwtDalHelper`/`AD_User.username` already relies on to link an `AD_User` row to its `etgo_account` row by matching value. Because generated code has no beforeSave-derivation support (see `docs/possible-limitations.md` L1), the copy is enforced server-side: `UserRoleAssignmentHandler.handle()` (`com.etendoerp.go`) rewrites the `POST` request body's `username` to the trimmed/lower-cased `email` before the default create runs, and rejects a blank/missing email with 400. On a successful create, `UserRoleAssignmentHandler.afterHandle()` reads the created record's `email`/`name` back out of the response and provisions a matching `etgo_account` row in `pending` status (no password) via `EtendoGoAccountProvisioning.ensurePendingAccount` — best-effort, never failing the parent `AD_User` creation. The account stays unusable (cannot log in) until ETP-4830's invite-email flow sets a password and flips `ETGO_ACCOUNT.STATUS` to `active` — that transition is ETP-4830's responsibility, not implemented here.

**Temporary admin-set-password workaround (ETP-4829):** the create form's existing `password` field (previously only mapped to `AD_User.Password`, Openbravo's own classic-backend login) doubles as an optional way to skip the pending state until ETP-4830 ships. If the admin types a password there on create, `UserRoleAssignmentHandler.handle()` validates it against `PasswordPolicy.isStrong` (same rule as self-service register) and rejects a weak one with 400; on success, `afterHandle()` creates the `etgo_account` already `active` with that password (hashed via the extracted `PasswordHasher.hash`, the same algorithm `EtendoGoJwtServlet` uses for register/login/password-reset). Leaving the field blank falls back to the pending path above. `AD_User.Password` itself is unaffected either way.

## Interaction model
- Route: `/user` for the list and `/user/:recordId` for the record detail.
- Visibility: visible in System > Settings from `tools/app-shell/src/menu.json`; it is not marked hidden.
- Implementation type: generated window loaded from `tools/app-shell/src/windows/registry.js` into the shared app-shell list/detail flow.
- Window shape: master-child in the contract (`user` + `emailConfiguration`), but no child entity is mounted on the detail page. The native `userRoles` child (`AD_User_Roles`, ETP-4512) was `exclude: true`d in `decisions.json` (ETP-4906 manual-QA fix, wave 6) — it used to render as its own read-only secondary tab sharing the exact same translated label ("Roles del usuario") as ETP-4906's new custom tab below, leaking the internal "Personal – &lt;user&gt;" composition role to the admin. It no longer renders at all; the orphaned `UserRolesTable.jsx`/`UserRolesForm.jsx` generated output was deleted (ETP-4906 REVIEW cleanup) once a clean `make regen ONLY=user` was confirmed to no longer emit them.
- List behavior: the generated page exposes list filtering by `name` and `email` (`username` removed from filters and the grid — ETP-4829). The grid also renders a role-chips column (`RoleChipsCell`, `window.customComponents.headerTable: "UserHeaderTable"`) and a toolbar role filter (`RoleFilterControl`) — see "Role assignment — multi-role composition (ETP-4906)" above.
- Detail behavior: the detail page renders the main user form, the multi-role chip control (`AssignTemplateRolesControl`, headerExtra), and a "Roles del usuario" custom tab (`window.customPanelTabs`, live permission-preview matrix, existing-user only) — the only "Roles del usuario" surface on this window since the native `userRoles` tab was excluded (see Window shape above).
- An **Attachments** tab is available in the detail tab strip, allowing files to be attached to the current record.
- **Tab strip order (ETP-4906, DEV wave 10):** Roles del usuario, Configuración del correo electrónico, Adjuntos — in that fixed order. `windows/custom/user/index.jsx` sets `tabOrder: 0` on the `roles` custom tab and passes `detailTabOrder={1}` through to the generated `UserPage`/`DetailView`. Both are required: "Configuración del correo electrónico" is not a plain `secondaryTabs` entry — the generated page renders it via `DetailTable={EmailConfigurationTable}`, which `DetailView.jsx`'s `buildInitialTabs` (`detailViewHelpers.jsx`) treats as the special LINES-tab slot, defaulting to weight `LINES_DEFAULT_WEIGHT = -1` when no `detailTabOrder`/`detailTabIndex` is set — lower than `roles`' own `tabOrder: 0`, which is what made an earlier fix that only touched `tabOrder` silently ineffective. `attachments` is left at its implicit default weight (999) so it keeps sorting last.

**Save-lifecycle hook (`onAfterExistingSave`, ETP-4906).** `AssignTemplateRolesControl`'s selection is local-only until the user clicks Guardar — the shared `DetailView.jsx` component (`tools/app-shell/src/components/contract-ui/DetailView.jsx`) now supports an `onAfterExistingSave(saved, {token, apiBaseUrl})` prop, invoked exactly once per save click, only when `!isNew` (i.e. never before an `AD_User_ID` exists). It mirrors the existing `onAfterCreate` prop's call shape but fires on the *existing-record* save path instead of the create path. This is a **generic, reusable extension point on the shared component** — not a `user`-window-specific hack — any other custom window can pass the same prop to run a side-effecting call after an existing record is saved, exactly the way `windows/custom/warehouse/index.jsx`'s `onAfterCreate` wiring is the precedent this pattern was copied from. Today `user` is the only window that uses it (wired in `windows/custom/user/index.jsx`, which also passes `additionalDirtyState` — a pre-existing `DetailView.jsx` prop, not new — so a role-only chip change enables Guardar even though it never touches a form field).


## Reactive behavior and dependencies
- Identity synchronization is implied for Name, First Name, and Last Name because all three fields carry the same `SL_User_Name` callout in the contract. The evidence supports that these fields are intended to react together, but the exact visible UX of that synchronization is not shown in the current SPA code.
- Business Partner and Supervisor are search selectors, so they depend on lookup results rather than free-text entry.
- Default Role's read-only *value* remains the parent context for two dependent defaults: Default Client and Default Organization both depend on it, unaffected by ETP-4512/ETP-4906 (neither the legacy `AssignRoleControl` nor its ETP-4906 replacement `AssignTemplateRolesControl` writes `defaultRole` anymore — the field is now purely a display value on this window).
- Default Warehouse depends on Default Client, so warehouse availability should narrow after the client is chosen.
- The native User Roles child (ETP-4512) is excluded from this window entirely as of ETP-4906 (see Window shape above) — `Default_Ad_Role_ID`'s single-row sync (`UserRoleAssignmentHandler`) is unaffected server-side, there is simply no UI surface for it anymore.
- The "Roles del usuario" tab (`UserRolesTab`, ETP-4906) reacts live to `AssignTemplateRolesControl`'s chip toggles with **zero extra network calls per toggle** — it fetches its data once on mount via `Promise.all([fetchMenuTree(), fetchRolesOverview(), fetchTemplateRoles()])` (`SFListMenu`'s menu tree, `SFRolesOverview`, and `SFSystemRoleTemplates`), then reads the shared, not-yet-saved role selection from `roleSelectionContext.js`'s `useRoleSelection()` and recomputes the matrix purely from already-fetched data. **Two role sources, two different jobs (DEV wave 7):** the matrix's own columns (which roles, and their per-window tier data) come from `fetchTemplateRoles()` (`SFSystemRoleTemplates`) — the 4 fixed system-level templates; `fetchRolesOverview()` (`SFRolesOverview`) is kept only for the `activeWindowIds` filter below, since it needs the union across ALL of the calling tenant's roles including its client-admin row (a few real windows are deliberately granted to none of the 4 templates but must still appear as `—` rows), which `SFSystemRoleTemplates`'s response can't supply on its own. It renders one column per currently-selected non-admin template role and one row per menu window (grouped by category, in menu order), filtered down to only windows Etendo GO actually exposes — the union of every `windows[].id` across ALL of `SFRolesOverview`'s roles (Admin included), which drops classic-only AD menu entries (e.g. Application Dictionary) that `SFListMenu`'s tree still returns but Etendo GO never surfaces; any category left with zero surviving rows is omitted entirely (ETP-4906 manual-QA fix, wave 6) — plus 3 hardcoded "General" rows (`Inicio (Dashboard)`, `Favoritos`, `Copilot (Asistente IA)`) rendered as always-✓ for every column since they have no `AD_Window_ID` to derive access from; 9 other windowless rows documented in `com.etendoerp.go`'s `TemplateRoleWindowAccess` javadoc are intentionally omitted entirely (never rendered, not even as a `—` row). Cell values: `✓` (full access), `Solo lectura` (read-only), `—` (absent from that role's `windows[]`). Shows an empty state when zero roles are currently selected. Rendered only for an existing user — `onVisibilityChange(!isNew)` hides the tab entirely while creating a new user.
- Security state is visible but not user-driven in the current form: Expired Password, Locked, and Last Password Update are read-only fields or summary values.
- No status-driven actions are visible in current evidence. `statusField` is `null`, `extraBadges` is empty, and the page-level `processes` array is empty in `UserPage.jsx`.
- No totals, discount, tax, or document-style recalculation behavior is visible in current evidence for this window.

## Gap assessment
- `UserPage.jsx` mounts `emailConfiguration` as its detail child entity (`detailEntity="emailConfiguration"`, `DetailTable={EmailConfigurationTable}`, `DetailForm={EmailConfigurationForm}`) — the native `userRoles` entity no longer exists in the contract at all (`exclude: true`d since DEV wave 6), so it is not a candidate detail slot; `emailConfiguration` became the page's only detail entity as a result. This is no longer a gap — see Manual verification step 7.
- The contract's `smtpconnectiontest` action for `emailConfiguration` is exposed: `UserPage.jsx` declares a `detailProcesses` array containing `smtpconnectiontest` ("Test SMTP Connection"), wired to the email-configuration detail pane described above.
- The contract includes `processNow` and `grantPortalAccess` actions on the parent user entity, but the generated detail page exposes no visible process buttons. This is an open gap between contract capability and current page behavior.
- The shared shell supports defaults loading for new records, but there is no user-window-specific evidence here showing what user defaults are prefilled by the backend for a new record.
- The callout-backed synchronization between Name, First Name, and Last Name is suggested by the contract, but the current evidence does not prove the exact browser interaction, so it should not be treated as confirmed UI behavior without manual verification.

## Manual verification
1. Open `/user` and confirm the list can locate records by `name` and `email`, and that no `username` column or filter is visible.
1a. Create a new user from `/user` with a valid email and confirm it saves; confirm the AD_User's `username` was set to the email (lower-cased) and a matching `etgo_account` row exists in `pending` status. Attempt to create a user with a blank email and confirm the request is rejected (400).
2. Open `/user/:recordId` and confirm the form shows identity fields, Business Partner and Supervisor lookup fields, security indicators, and default selectors.
3. On an existing user, open the header's role chip control (`AssignTemplateRolesControl`) and toggle 2+ template roles (Finance/Sales/Purchasing/Inventory) on; confirm chips appear/collapse with "+N" overflow and Guardar becomes enabled even though no other field changed. Open the "Roles del usuario" tab and confirm one column appears per currently-toggled role, instantly, with the correct General rows (`Inicio (Dashboard)`, `Favoritos`, `Copilot (Asistente IA)` always ✓) and category-grouped window rows.
4. Click Guardar; confirm it calls the role-assignment save exactly once, Guardar disables again afterward, and reloading the record shows the same roles still selected (persisted). Confirm the row for this user in the `/user` list shows the same roles as chips (`RoleChipsCell`, translated labels) with "+N" overflow when there are more than 2.
5. Toggle a role off, save, and confirm the matrix tab drops that role's column and the grid chip for that user updates accordingly (never leaves a stale/duplicate entry).
5a. Use the Users list toolbar's role filter (`RoleFilterControl`) to filter by a template role, then by "Administrador"; confirm the grid narrows to matching rows in both cases (a classic-Admin user's `defaultRole` counts as a match for the Admin filter even though it has no composed template roles).
5b. Attempt to open the role chip control / "Roles del usuario" tab while creating a brand-new user; confirm the control shows a save-first placeholder and the tab is hidden entirely until the user is saved once.
6. Confirm Expired Password, Locked, and Last Password Update are displayed as review state rather than normal editable business fields.
7. Confirm the current page surfaces an Email Configuration child pane (`DetailTable={EmailConfigurationTable}`/`DetailForm={EmailConfigurationForm}`) with a "Test SMTP Connection" action available from it. Confirm it does NOT surface a Process Now action or a Grant Portal Access action (both remain unexposed gaps — see Gap assessment).
8. Open a saved record and confirm the **Attachments** tab is visible in the tab strip. Upload a file and verify it appears in the table. Download it and delete it. When multiple files exist, confirm 'Download all (ZIP)' and 'Delete all' appear in the table header and that 'Delete all' shows a confirmation dialog before removing all files.
