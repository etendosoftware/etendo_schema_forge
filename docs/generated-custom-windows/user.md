# User

## Intent
This window should let administrators maintain a person’s application identity, review basic security state, define default working context, and assign the roles that control what the user can do in the system.

## What this window should allow
Users should be able to:
- create, find, open, update, and delete user records;
- maintain identity fields such as Name, Email, Description, Position, and Phone (First Name/Last Name were discarded from this window in ETP-4906 wave 12 — see "Reactive behavior and dependencies" below); Email becomes read-only once the record is saved (ETP-4830 — see "Invite-on-create flow" below);
- connect the user to a Business Partner and Supervisor through search-based selectors;
- set a Password only on an EXISTING user (ETP-4830 — the Password input no longer appears on the create form at all, since admin-typed passwords no longer bypass the invite-email flow; it reappears once the record is saved, for resetting an existing user's password) while reviewing read-only security indicators such as Expired Password, Locked, and Last Password Update;
- choose default context values for Language, Client, Organization, and Warehouse;
- assign 1+ system-level template roles (Finance/Sales/Purchasing/Inventory) to an existing user via a multi-select chip control in the header, see a live per-role permission-preview matrix in a dedicated "Roles del usuario" tab before saving, and read/filter each user's applied roles as chips from the Users list grid (ETP-4906, superseding the single-role picker from ETP-4512).

**Role assignment — multi-role composition (ETP-4906).** `AssignTemplateRolesControl` (`tools/app-shell/src/windows/custom/user/AssignTemplateRolesControl.jsx`, wired as `window.headerExtra.customForm`) replaces the old single-select `AssignRoleControl`. It renders the user's currently-selected template roles as removable chips (+N overflow when collapsed) with a checkbox list to add/remove roles, sourced from `fetchTemplateRoles()` (`SFSystemRoleTemplates`) — the 4 fixed system-level template roles (no `isClientAdmin` filter needed: that endpoint never returns a client-admin row at all, there being no such role at system level). **DEV wave 7 repointed this from the original `SFRolesOverview`-backed catalog** — `fetchRolesOverview()`/`SFRolesOverview` is still used elsewhere on this window (the grid's `activeWindowIds` window-exposure filter and `RoleChipsCell`'s admin-detection branch, see below), but no longer supplies the role/column catalog itself. Selection is **local-only until Guardar** — toggling a chip never calls `onChange('defaultRole', ...)` or fires any network request; it only mutates a shared selection held in React Context (`roleSelectionContext.js`, `useRoleSelection()`), consumed by the sibling "Roles del usuario" tab below for its live preview. `defaultRole` itself stays a read-only field on the detail form (unaffected by this control), and the control renders a save-first placeholder for a not-yet-persisted user (composition requires an `AD_User_ID` — never attempted on create). On Guardar, `windows/custom/user/index.jsx` (the window's custom wrapper, registered as `customLoaders['user']` in `tools/app-shell/src/windows/registry.js`) diffs the local selection against the set it fetched on load (`fetchUserRoleAssignments(userId)`, `tools/app-shell/src/lib/userRoleAssignmentsApi.js`) and, only if it actually changed, calls `saveUserRoleAssignments(userId, templateRoleIds)` — a thin wrapper around the existing `SFAssignUserRoles` webhook, which fires exactly once with the FULL desired set (a set-reconciliation call, not additive). On the backend, `SFAssignUserRoles`/`UserRoleCompositionService` (`com.etendoerp.go`) resolve or create the user's personal composition role and reconcile its `AD_Role_Inheritance` rows against the desired template ids — the same most-permissive-wins composition model ETP-4852 already built, unrelated to the legacy `AD_User_Roles`/`Default_Ad_Role_ID` single-row sync ETP-4512 introduced.

**Owner/admin composition lock (ETP-5019).** A user currently holding the tenant's client-admin "Admin" role already has full access by construction — composing template roles for it would fail to find a reusable personal role (Admin is explicitly excluded from reuse) and silently mint a brand-new one, replacing `Default_Ad_Role_ID` and losing the Admin role as a side effect. `AssignTemplateRolesControl` now detects this up front (comparing the record's resolved default role id against `SFRolesOverview`'s `isClientAdmin` row, the same pattern `RoleChipsCell.jsx`'s admin-detection branch already used) and renders a locked message (`data-testid="AssignTemplateRolesControl__admin-locked"`, i18n key `adminRoleNoCompositionMessage`) instead of the interactive chip editor — this is UX-only, so it still shows correctly even before the roles fetch resolves. The real enforcement lives on the backend: `UserRoleCompositionService#enforceOwnerProtection` now unconditionally rejects composition when the target is the flagged ETP-4830 owner (`OwnerSupport.isOwner`) **or** currently holds the client-admin role (`getDefaultRole().isClientAdmin()`), whichever signal fires — self-service by the owner used to be allowed and silently overwrote their own Admin role with an empty personal role; that exception is now removed regardless of which of the two signals applies.

**Company user invitations, standalone endpoint (ETP-4894, superseded as the window's primary flow by ETP-4830 below):** `com.etendoerp.go` still exposes an email-only `company-invitation` webhook (`POST /sws/go/company-invitations`) and its own public acceptance page (`InviteAcceptancePage`, `/invite?token=...`), for inviting an *existing* `AD_User` (with roles already assigned) that has no Go account yet. The frontend modal that drove it, `InviteUserDialog.jsx` (`tools/app-shell/src/windows/custom/user/InviteUserDialog.jsx`), is **no longer wired into this window** (ETP-4830 disconnected it from `index.jsx` — see below) but is deliberately kept intact, unwired, as a distinct future entry point for that one case; it is not currently reachable from any menu or button in the app.
- If the invitee already has an active Etendo Go account, they accept the invitation in 1 click (`POST /sws/go/company-invitations/accept`), linking that account to the prepared `AD_User`.
- If the invitee is new, they fill in their display name and set a strong password (`POST /sws/go/company-invitations/register-and-accept`), creating an `Account` locked to the invitation email and linking it to the prepared `AD_User` without changing its roles.
- All invitation lifecycle events (`PENDING`, `SENT`, `ACCEPTED`, `EXPIRED`, `REVOKED`) are recorded in `ETGO_INVITATION` using SHA-256 hashed bearer tokens. Password resets are not repurposed as pseudo-invitations.
- An authenticated Etendo Go account can retrieve its own invitations through `GET /sws/go/company-invitations/mine`. The server derives the account email from the bearer session, so invitations from multiple companies are included while invitations addressed to other accounts remain excluded.

**Invite-on-create flow, the window's primary invitation path (ETP-4830).** Creating a NEW user from this window no longer offers an admin-typed-password bypass — `com.etendoerp.go` always sends the invite email on creation, and the create form reflects that:
- The Password field (`displayLogicJs: "!!record.id"` in `decisions.json`) is hidden entirely on the create form and reappears once the record is saved, for resetting an existing user's password — a separate, still-valid use of the same native field, unrelated to invitation.
- Email (`readOnlyLogicJs: "!!record.id"`) becomes read-only once the record is persisted — it seeds `username` and the linked `etgo_account` row at creation time only, so editing it afterward would desync the two (same "locks after first save" pattern as `sales-invoice`/`purchase-invoice`'s `transactionDocument`, see `docs/decisions-reference.md`).
- A pending-invitation status pill renders in the detail toolbar's Cancel-button row (`PendingInvitationPill`, wired via `UserPage`'s generic `topbarExtra` slot — not a `decisions.json` extension point, since the field is a multi-state enum `extraBadges`/`statusPills` cannot express) whenever the record's `invitationStatus` field reads `"PENDING"` or `"SENT"` — amber, "Invitación pendiente" (`PENDING` is only the transient pre-send state within the create request; `SENT` is the real persisted status once the email goes out, and both render the same pill since an invite is outstanding either way). `"DELIVERY_FAILED"` renders its own red "Error al enviar la invitación" pill. `"EXPIRED"` renders a neutral (gray) "Invitación caducada" pill (ETP-4830 item #2/#3 addition — see below; this became a genuinely reachable value once `CompanyInvitationService#findLatestInvitationStatus` started computing it live from `expiresAt` instead of relying on a stored column nothing ever wrote). `"ACCEPTED"` renders a green (success) "Invitación aceptada" pill (ETP-4999 — a blank cell for an accepted invitation used to read as "no invitation was ever sent", misleading for a user who already accepted theirs). `"REVOKED"` and `null` still render nothing. Matches the confirmed `com.etendoerp.go` `invitationStatus` contract (present on every `user` GET response, list and single-record alike).
- **The same pill now also renders as its own "Invitation" column on the Users list grid** (scope addition to ETP-4830, requested after the detail-toolbar pill above already shipped). `PendingInvitationPill` was extracted into its own file (`tools/app-shell/src/windows/custom/user/PendingInvitationPill.jsx`, `status` in, pill-or-`null` out) so the detail toolbar and the grid column share ONE `invitationStatus` → visual-treatment mapping instead of two — see "List behavior" below for the grid column itself.
- On successfully creating a new user, a single actionable toast reads "Usuario creado. Invitación enviada por correo." with a "Configurar roles" action (`handleAfterCreate`, wired via `UserPage`'s `onAfterCreate`) — clicking it re-navigates to the saved record with `location.state.openSecondaryTab: 'custom:roles'` (the same tab-switch mechanism `DetailView.jsx` already uses internally) to open the "Roles del usuario" tab, and scrolls/focuses `AssignTemplateRolesControl` (a separate surface — the `formFooter`, not inside any tab panel). The toast reuses `useEntity.js`'s own generic "record created" toast id (`RECORD_SAVE_TOAST_ID`) instead of dismissing and re-creating it — `toast.success(msg, { id: RECORD_SAVE_TOAST_ID })` updates that toast in place, so only one toast is ever visible without the `dismiss()`-then-create() race that could otherwise drop the toast entirely (sonner schedules `dismiss()` via `requestAnimationFrame`; a new toast mounted before that frame runs would be dismissed as if it were the old one).
- **Backend ordering, invisible in this window's UI but load-bearing (ETP-4830 item #14, human-directed requirement "create user → assign personal role → invite"):** `com.etendoerp.go`'s `POST /user` post-hook mints the new user's own empty personal composition role (`UserRoleCompositionService#createFreshPersonalRole`, never the get-or-create `ensurePersonalRole` — a brand-new user can never legitimately reuse someone else's orphaned role) BEFORE sending the invitation email, proven by a call-order test, not just "both ran". `AssignTemplateRolesControl` still shows its save-first placeholder for a not-yet-persisted record either way (see "Role assignment — multi-role composition" above) — this ordering has no visible effect on the create form itself, it only guarantees the user already has its own role identity, with correct org access and defaults (see `com.etendoerp.go`'s `docs/neo-headless.md` §8d "Org access + user defaults on creation"), by the time the invite goes out. See "Gap assessment" below for the bug this superseded (a stale `defaultRole` getting reused instead of a fresh role being minted).

**Resend invitation (ETP-4830 item #2).** An admin-triggered "Reenviar invitación" button (`ResendInvitationButton`, `windows/custom/user/index.jsx`) renders next to the pill in the detail toolbar, visible only when `invitationStatus` is `PENDING`/`SENT`/`EXPIRED`/`DELIVERY_FAILED` (`REVOKED` and `ACCEPTED` are excluded — a revoked invite must not be silently resurrected by a click, and an accepted one has nothing left to resend). Backed by a new NEO pseudo-spec bridge webhook, `SFResendInvitation` (`com.etendoerp.go`, real/always-on — no dev-only feature flag, unlike the debug bypass below), calling `CompanyInvitationService#resendInvitation`: if the current invitation is still open (`PENDING`/`SENT`, not yet expired) it is marked `REVOKED` first, so the old link stops working the instant the fresh one is issued, then a brand-new token/row is minted and sent — reusing the same mint-and-send mechanics `createInvitation` itself uses (extracted into a shared private `issueFreshInvitation` helper). On success the button's `onRefresh` callback re-fetches the record so the pill reflects the real send outcome (`SENT` or `DELIVERY_FAILED`) instead of assuming success optimistically. Frontend client: `tools/app-shell/src/lib/resendInvitationApi.js`.

**Owner badge (ETP-4830 item #4).** A small neutral (gray) "Owner" pill renders for the ONE `AD_User` per client flagged via `EM_ETGO_Is_Owner` (see `docs/neo-headless.md` §7 item 10 for the full backend mechanism — the write-path protection that already existed, and the "Assignment"/"Baseline" caveats: pre-existing tenants have no owner marked until a separate, not-yet-built backfill runs). `isOwner` is a backend-contract-only boolean the `user` NeoHandler attaches to every GET response row (`UserRoleAssignmentHandler#attachOwnerFlag`, the exact same pattern already established for `invitationStatus`) — not an `AD_User` column at all, so like `invitationStatus` there is nothing for `decisions.json`/the generator to emit. Two DIFFERENT presentations, by design, in the two surfaces that show it:
- **Detail header's `TopbarExtra`** — a real `DocumentStatusPill`-based badge (`OwnerBadge`, `windows/custom/user/OwnerBadge.jsx`), first item, before the invitation pill (a static identity marker about the account rather than a workflow state). Renders nothing for `false`/absent.
- **Users list grid — human call, after first shipping a dedicated column: at most ONE user per client is ever flagged owner, so a whole grid column was disproportionate space for something that rare.** Reworked into a small inline pill on the `name` cell instead, via `renderDefaultCell`'s existing declarative `col.pill` mechanism (`DataTable.cellRenderers.jsx` — `{ when(row), label, className? }`, already built and tested for exactly "badge attached to the first visible string column" before this ticket ever used it) — no new grid column, no new render function, just a `pill` config added to the `name` column in `UserHeaderTable.jsx`.

**Active/inactive toggle ("Activo", ETP-4830).** The ticket's reference screenshot places the pending-invite pill next to an "Activo" active/inactive toggle in the detail header, and shows an equivalent "Activo" column in the Users list grid. Both are now built, both live-PATCH `AD_User.IsActive` (`active` field), and de-activating a user only flips that flag — it never deletes the `AD_User` record or blocks an admin from still opening/editing it afterward (standard Etendo de-activation semantics; see this field's own AD help text quoted in its `decisions.json` field decision).
- **Grid column.** `active` was overridden in `decisions.json` from the raw AD default (`visibility: "system"`, hardcoded `derivation: {type: "computed", source: "true"}` — always `true`, never rendered) to `visibility: "editable"` + an explicit `"derivation": null` (the escape hatch documented in `resolve-curated.js` for a system→editable transition — without it, the raw computed derivation would still get copied onto the curated field and NEO would keep overriding any admin-set value on save; `purchase-order`/`sales-order`/`sales-quotation`/`purchase-invoice`/`sales-invoice`'s `currency`/`transactionDocument` fields use the exact same pattern) plus `inlineToggle: true` (renders as a live-PATCHing `Switch`, `generate-frontend.js`'s existing `togglePart`/`DataTable.cellRenderers.jsx`'s `renderBooleanCell` — no generator change needed). Because this window's list grid is fully taken over by `UserHeaderTable.jsx` (`window.customComponents.headerTable`, ETP-4906 — it bypasses the plain generated `UserTable.jsx` entirely), the `active` column had to be added a second time, by hand, to `UserHeaderTable.jsx`'s own hardcoded `columns` array (mirroring what the generated table already emits: `{ key: 'active', column: 'IsActive', type: 'boolean', toggle: true, required: true }`) — the declarative `decisions.json` flag alone is not sufficient for this window.
- **Detail-header toggle.** `ActiveStatusToggle` (`windows/custom/user/index.jsx`) is rendered alongside `PendingInvitationPill` inside a new composite `TopbarExtra` component, wired to `UserPage`'s `topbarExtra` slot (pill-then-toggle order — the reference screenshot's exact order wasn't pixel-verifiable, so this is the reasonable default). Hidden entirely on a not-yet-saved record (no `id` to PATCH against yet — same guard `AssignTemplateRolesControl` uses for its own save-first placeholder). It reuses `runInlineToggleRequest` — exported from `DataTable.jsx` for exactly this reuse (ETP-4830) — for the identical PATCH + optimistic-update + error-toast behavior the grid's own inline toggles already have, instead of re-implementing that logic a second time.

## Interaction model
- Route: `/user` for the list and `/user/:recordId` for the record detail.
- Visibility: visible in System > Settings from `tools/app-shell/src/menu.json`; it is not marked hidden.
- Implementation type: generated window loaded from `tools/app-shell/src/windows/registry.js` into the shared app-shell list/detail flow.
- Window shape: single-entity in the contract (`user` only). `emailConfiguration` (the "Configuración del correo electrónico" child, SMTP settings) was `exclude: true`d in `decisions.json` (ETP-4999 — removed from the Users window tab strip entirely, not relevant to this window); its generated `EmailConfigurationTable.jsx`/`EmailConfigurationForm.jsx` were deleted once a clean `make regen ONLY=user` confirmed they were no longer emitted, same "delete the now-orphaned generated output" step ETP-4906 already used for `userRoles` below. The native `userRoles` child (`AD_User_Roles`, ETP-4512) was `exclude: true`d in `decisions.json` (ETP-4906 manual-QA fix, wave 6) — it used to render as its own read-only secondary tab sharing the exact same translated label ("Roles del usuario") as ETP-4906's new custom tab below, leaking the internal "Personal – &lt;user&gt;" composition role to the admin. It no longer renders at all; the orphaned `UserRolesTable.jsx`/`UserRolesForm.jsx` generated output was deleted (ETP-4906 REVIEW cleanup) once a clean `make regen ONLY=user` was confirmed to no longer emit them.
- List behavior: the generated page exposes list filtering by `name` and `email` (`username` removed from filters and the grid — ETP-4829). The grid also renders a role-chips column (`RoleChipsCell`, `window.customComponents.headerTable: "UserHeaderTable"`), a toolbar role filter (`RoleFilterControl`) — see "Role assignment — multi-role composition (ETP-4906)" above — an "Activo" inline-toggle column (ETP-4830, `active` field's `inlineToggle: true` in `decisions.json`, hand-mirrored into `UserHeaderTable.jsx`'s own column list — see "Active/inactive toggle" above), and an "Invitation" column (ETP-4830 scope addition) placed immediately before the role-chips column, rendering the same `PendingInvitationPill` as the detail toolbar per row — blank for `null`/`REVOKED`/unrecognized statuses, amber for `PENDING`/`SENT`, red for `DELIVERY_FAILED`, neutral gray for `EXPIRED`, green for `ACCEPTED` (ETP-4999 — a blank cell for an accepted invitation used to read as "no invitation was ever sent", which is misleading for a user who already accepted theirs). `invitationStatus` is not an `AD_User` column at all (a backend-contract-only field NEO adds to every `user` response), so it has no `decisions.json`/generated-table counterpart to mirror — it is declared entirely by hand in `UserHeaderTable.jsx`. `isOwner` (ETP-4830 item #4) is NOT a grid column — see "Owner badge" above for why: it renders as a small inline pill on the `name` cell instead. The list's Print buttons (bulk "Print (N)" + toolbar Print/Report) are hidden (ETP-4999, `listViewOptions.hidePrint: true` in `decisions.json` — Users is not a document-type window, so the generic print mechanism doesn't apply here; see "Print visibility" below).
- **Contact-only rows excluded from the list (ETP-5019).** A `Business Partner Contact` created from the BP window's "Contacts" tab auto-creates its own `AD_User` row purely to carry contact info (e.g. "Default Customer Contact"), never meant to log in or hold roles — these rows used to leak into the Users list for every client. `UserRoleAssignmentHandler#excludeContactOnlyUsers` (`com.etendoerp.go`), a pre-hook on the `user` list `GET` (record id absent), injects a `_neoWhere` predicate — `e.username is not null and e.username <> ''` — before the default CRUD list fetch runs, rather than post-filtering the response rows (post-filtering after the DB-level `LIMIT`/`OFFSET` had already applied would corrupt pagination). The signal is structural, not a name match on "Contact": every genuinely login-capable `AD_User` always gets a non-blank `username` (this same handler derives one from `email` on every create — see "Invite-on-create flow" above), even one with zero roles assigned yet, so filtering on `username` blankness — unlike role count — never hides a legitimate not-yet-assigned real user. Entirely backend-side; nothing in `decisions.json`/the generated `UserHeaderTable.jsx` filters changed.
- Detail behavior: the detail page renders the main user form, the multi-role chip control (`AssignTemplateRolesControl`, headerExtra), and a "Roles del usuario" custom tab (`window.customPanelTabs`, live permission-preview matrix) — the only "Roles del usuario" surface on this window since the native `userRoles` tab was excluded (see Window shape above). As of ETP-4999, the tab stays visible even for a brand-new, not-yet-saved user — it shows the SAME "Selecciona un rol para visualizar los permisos" empty-state placeholder an existing user with zero roles selected sees (a new user can never have any roles selected before its first save either, so the two states are identical) — see "Reactive behavior and dependencies" below. The toolbar row (Cancel button + status area) also renders an owner badge when applicable, a pending-invitation pill when applicable, a "Reenviar invitación" button when the status is resend-eligible, and an "Activo" active/inactive toggle for an existing record (ETP-4830, `topbarExtra` — see "Owner badge", "Invite-on-create flow", "Resend invitation", and "Active/inactive toggle" above). The detail-view Print button is hidden unconditionally (ETP-4999, `window.hidePrint: true` — see "Print visibility" below).
- An **Attachments** tab is available in the detail tab strip, allowing files to be attached to the current record.
- **Print visibility (ETP-4999).** The Print button is hidden in both the detail-view action bar and the list view (`window.hidePrint: true` + `window.listViewOptions.hidePrint: true` in `decisions.json`) — Users is not a "document" window (no `documentNo`/completion flow), so the plain unconditional `hidePrint` boolean is the right mechanism here, not the conditional `hidePrintWhen` used by document windows. See `docs/decisions-reference.md` → "Print Visibility" for the general mechanism.
- **Tab strip order (ETP-4906, DEV wave 10; ETP-4999 update):** Roles del usuario, Adjuntos — in that fixed order. `windows/custom/user/index.jsx` sets `tabOrder: 0` on the `roles` custom tab so it sorts before `attachments` (implicit default weight 999). "Configuración del correo electrónico" used to sit between the two (requiring a `detailTabOrder={1}` prop to land in the right place, since it occupied the special LINES-tab slot) — both the tab and that ordering prop were removed in ETP-4999 once `emailConfiguration` was excluded from the window entirely (see Window shape above).

**Save-lifecycle hook (`onAfterExistingSave`, ETP-4906).** `AssignTemplateRolesControl`'s selection is local-only until the user clicks Guardar — the shared `DetailView.jsx` component (`tools/app-shell/src/components/contract-ui/DetailView.jsx`) now supports an `onAfterExistingSave(saved, {token, apiBaseUrl})` prop, invoked exactly once per save click, only when `!isNew` (i.e. never before an `AD_User_ID` exists). It mirrors the existing `onAfterCreate` prop's call shape but fires on the *existing-record* save path instead of the create path. This is a **generic, reusable extension point on the shared component** — not a `user`-window-specific hack — any other custom window can pass the same prop to run a side-effecting call after an existing record is saved, exactly the way `windows/custom/warehouse/index.jsx`'s `onAfterCreate` wiring is the precedent this pattern was copied from. Today `user` is the only window that uses it (wired in `windows/custom/user/index.jsx`, which also passes `additionalDirtyState` — a pre-existing `DetailView.jsx` prop, not new — so a role-only chip change enables Guardar even though it never touches a form field).


## Reactive behavior and dependencies
- **First Name/Last Name were discarded from this window (ETP-4906, DEV wave 12, commit `404a0ce70`).** Both fields duplicated the mandatory Name field's Spanish label ("Nombre" for `Name` and for `Firstname` alike, per `es_ES.json`), and no manual-QA test user during this ticket ever used the auto-compose path. `firstName`/`lastName` are now `visibility: "discarded"` in `decisions.json` (removed from both the header form and the list grid), and the `SL_User_Name_Firstname`/`SL_User_Name_Lastname` rule decisions were flipped from `"Keep"` to `"Omit"` to match, alongside the pre-existing `SL_User_Name_Name` `"Omit"` decision — there is no longer a Name/First Name/Last Name synchronization callout on this window at all; Name is now typed directly with no auto-compose behavior.
- Business Partner and Supervisor are search selectors, so they depend on lookup results rather than free-text entry.
- Default Role's read-only *value* remains the parent context for two dependent defaults: Default Client and Default Organization both depend on it, unaffected by ETP-4512/ETP-4906 (neither the legacy `AssignRoleControl` nor its ETP-4906 replacement `AssignTemplateRolesControl` writes `defaultRole` anymore — the field is now purely a display value on this window).
- Default Warehouse depends on Default Client, so warehouse availability should narrow after the client is chosen.
- The native User Roles child (ETP-4512) is excluded from this window entirely as of ETP-4906 (see Window shape above) — `Default_Ad_Role_ID`'s single-row sync (`UserRoleAssignmentHandler`) is unaffected server-side, there is simply no UI surface for it anymore.
- The "Roles del usuario" tab (`UserRolesTab`, ETP-4906) reacts live to `AssignTemplateRolesControl`'s chip toggles with **zero extra network calls per toggle** — it fetches its data once on mount via `Promise.all([fetchMenuTree(), fetchRolesOverview(), fetchTemplateRoles()])` (`SFListMenu`'s menu tree, `SFRolesOverview`, and `SFSystemRoleTemplates`), then reads the shared, not-yet-saved role selection from `roleSelectionContext.js`'s `useRoleSelection()` and recomputes the matrix purely from already-fetched data. **Two role sources, two different jobs (DEV wave 7):** the matrix's own columns (which roles, and their per-window tier data) come from `fetchTemplateRoles()` (`SFSystemRoleTemplates`) — the 4 fixed system-level templates; `fetchRolesOverview()` (`SFRolesOverview`) is kept only for the `activeWindowIds` filter below, since it needs the union across ALL of the calling tenant's roles including its client-admin row (a few real windows are deliberately granted to none of the 4 templates but must still appear as `—` rows), which `SFSystemRoleTemplates`'s response can't supply on its own. It renders one column per currently-selected non-admin template role and one row per menu window (grouped by category, in menu order), filtered down to only windows Etendo GO actually exposes — the union of every `windows[].id` across ALL of `SFRolesOverview`'s roles (Admin included), which drops classic-only AD menu entries (e.g. Application Dictionary) that `SFListMenu`'s tree still returns but Etendo GO never surfaces; any category left with zero surviving rows is omitted entirely (ETP-4906 manual-QA fix, wave 6) — plus 3 hardcoded "General" rows (`Inicio (Dashboard)`, `Favoritos`, `Copilot (Asistente IA)`) rendered as always-✓ for every column since they have no `AD_Window_ID` to derive access from; 9 other windowless rows documented in `com.etendoerp.go`'s `TemplateRoleWindowAccess` javadoc are intentionally omitted entirely (never rendered, not even as a `—` row). Cell values: `✓` (full access), `Solo lectura` (read-only), `—` (absent from that role's `windows[]`). Shows an empty state when zero roles are currently selected. **The tab itself is always visible (ETP-4999)** — `onVisibilityChange(true)` unconditionally, even while creating a new user. A brand-new, not-yet-saved user renders the same empty-state placeholder directly (no fetches — `AssignTemplateRolesControl` only lets roles be selected once `data?.id` exists, so a new user's role selection is always empty, making the "zero roles selected" empty state the only possible outcome); the `Promise.all([fetchMenuTree(), fetchRolesOverview(), fetchTemplateRoles()])` fetch above still only runs for an existing record. Before ETP-4999, the tab hid itself entirely (`onVisibilityChange(!isNew)`) while creating a new user, which made the placeholder inconsistent between the pre-save and post-save empty states for no functional reason.

## Debug mode (ETP-4830, item #4 — dev/QA-only)

Typing the sequence `debuguser` anywhere in the app (any page) activates a debug panel for
exercising the invite-email flow and the pending-invitation pill's states without a real email
round-trip. State persists in `localStorage` under key `etendo-debug-user` and survives page
refresh. Typing the sequence again deactivates it. Same shape as `fiscal-monitor`'s own
`debugfiscal`/`useDebugMode.js` convention (see that window's own "Debug mode" section) but a
fully independent module — `useUserDebugMode.js` — with its own localStorage key and keystroke
sequence; the two never interact.

The keydown listener itself only registers in a dev build (`import.meta.env.DEV`) — the panel
cannot be discovered by typing the sequence at all in a production build. This is a
discoverability nicety only: the real security boundary is server-side (see below), since a dev
build gate says nothing about which *backend* the SPA happens to be pointed at.

When active, `UserDebugPanel` appears as a fixed dark panel (top-right, z-index 9999), mounted on
the `/user` LIST page (`UserHeaderTable.jsx`) so it is reachable without already knowing a
specific user's route:
- **Email input** (with a `<datalist>` seeded from the grid's currently-loaded rows) plus a
  **"Force-accept invitation"** button — calls the backend to find-or-create an active
  `etgo_account` for that email and, if a matching `ETGO_INVITATION` row exists, flip it to
  `ACCEPTED`, skipping the real token/email round-trip entirely. A newly created account's
  temporary password is surfaced in the success toast.
- **Invitation status dropdown** (`PENDING`/`SENT`/`ACCEPTED`/`EXPIRED`/`REVOKED`/
  `DELIVERY_FAILED`) plus a **"Force status"** button — directly sets `ETGO_INVITATION.STATUS`
  for the given email, for visually exercising every `PendingInvitationPill` state (see
  "Invite-on-create flow" above) without waiting on real email delivery.

**The real security boundary is entirely server-side, not this panel.** Both actions call
`com.etendoerp.go`'s `SFDebugInvitationBypass` webhook (reached through the NEO pseudo-spec
bridge — `docs/neo-headless.md` §4.10–4.11, "Debug invitation bypass" subsection), which is gated
OFF by default via `GoRuntimeProperties.readBoolean("etendo.go.debug.invitationBypass",
"ETGO_DEBUG_INVITATION_BYPASS", false)` — checked in `NeoPseudoSpecDispatcher` BEFORE the webhook
is even constructed. Any environment that hasn't explicitly opted in (its own local
`Openbravo.properties`/env var) gets a plain 404 for this endpoint, zero DB access — so the panel
rendering behind a keystroke sequence is a UI-side discoverability gate on top of a real backend
boundary, never a substitute for it.
