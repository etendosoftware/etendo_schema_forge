# Chart of Accounts

## Intent
Maintain the account master used by finance users and provide a quick, read-only review of each account's debit, credit, and current balance from the same window.

## What this window should allow
- Browse the account list from the Finance menu.
- Search accounts by code, name, and account type.
- Create subaccounts from the list toolbar's New button ("Nueva subcuenta"), which defaults the parent to the row selected in the tree (ETP-5593).
- Open an existing account and update those same setup fields, except protected parent-like subaccounts whose 8-digit code ends in `0000`.
- Delete an account through the standard generated entity flow.
- The tree does not show debit, credit, or balance: those YTD columns were never rendered, and ETP-5593 removed them from the tree's column list (they only leaked into Sort and Print).
- Filter the tree by code/name (search box) or account type from the list toolbar row — matches on displayed leaf or virtual-folder code/name (including letter-suffixed codes such as `430A`) retain the matching folder and its relevant descendants, while account-type filtering remains applied to leaves; non-matching branches are hidden.
- Deactivate or reactivate an existing subaccount directly from the tree via an inline toggle (protected `0000`-suffixed placeholder subaccounts cannot be toggled).
- Toggle whether the account is active directly from the tree row; the form's own `isActive` control follows the same live-toggle behavior rather than staying read-only.

## Interaction model
- Route: `/chart-of-accounts` for the list and `/chart-of-accounts/:recordId` for record detail.
- Visibility: visible from the Finance menu as **Chart of Accounts**.
- Breadcrumb: `Finanzas / Plan de cuentas` — driven by `decisions.json → window.category: "finance"`, which the generated `ElementValuePage.jsx` resolves through `tMenu()` alongside the window name. ETP-4945 corrected this from `category: "accounting"`, which rendered the wrong section (`Contabilidad / Plan de cuentas`).
- Implementation type: generated window route loaded from the app-shell window registry.
- Window shape: single-entity window for `elementValue`, with the runtime custom grouped tree table at `artifacts/chart-of-accounts/custom/AccountTreeView.jsx` replacing the generated list table.
- Record detail titles use the account code (`searchKey`) rather than the internal record id.
- The window title's count badge shows the number of **root** accounts (e.g. 4: A, P, PYG, O), not leaves (ETP-5593). `hook.items.length` would only reflect one paginated batch of leaves, so the tree reports its own count through ListView's opt-in `onRecordCountChange` table prop, computed from the **unfiltered** tree (a filter does not change it). `window.hideRecordCount` is now `false`.
- The tree renders the FULL Etendo Classic account hierarchy as nested, expandable folders — matching Classic's "Combinación de cuentas" grouped view exactly. For example, account `20000000` nests 6 levels deep: `A` (Heading: ACTIVO) → `A.A` (Heading) → `A.A.I` (Heading) → `200` (Account) → `2000` (Breakdown) → `20000000` (Subaccount). Every folder is collapsed by default; expand/collapse state is persisted to `localStorage` (`sf.chartOfAccounts.expandedFolderIds`) so navigating away to another window and back restores exactly what the user left open.
- **One toolbar row (ETP-5593).** The tree renders no toolbar of its own. ListView's toolbar row holds, left to right: **Expandir todo / Contraer todo** · **Buscar** · **Tipo de cuenta**, then Compartir · Ordenar · Actualizar · Imprimir · **Nueva subcuenta**. The left group is `AccountTreeView.ToolbarQuickFilter` = `artifacts/chart-of-accounts/custom/ChartOfAccountsToolbarSlot.jsx` (ETP-5188 static-slot convention); the right group is ListView's own. Because the bar lives outside the `ScrollPane`, it stays visible while the tree scrolls — the old sticky controls wrapper is gone.
  - **Expandir todo / Contraer todo** is one dynamic button: "Expandir todo" (`ArrowDown`) while no shown folder is open; "Contraer todo" (`ArrowUp`) as soon as one is, whether it was opened by this button or by a row's chevron. Persisted ids of folders that no longer exist are ignored.
  - **Buscar** keeps the in-tree code/name search (decision Q1, 2026-10-05). The Top Bar search is a vector-search palette, which opens records rather than filtering the list, and Plan de cuentas is not onboarded to vector search. Removing this box is deferred until it is (follow-up ticket, not yet created). The box updates on every key, but it writes `q` to the URL, and so re-filters the tree, only after a 250 ms pause (`SEARCH_DEBOUNCE_MS`). Leaving the box writes a pending search at once (`onBlur`), so pressing Compartir or opening Tipo de cuenta right after typing sees it. URL writes start from the latest rendered params, not from react-router's functional `prev`: in the debounce timer that `prev` is stale, and it used to drop an account type picked during the pause (QA, ETP-5593).
  - **Tipo de cuenta** is the core `DistinctValuesFilter` with a `heading` (same component as Documentos no contabilizados): "Todos los tipos de cuenta" first, then the six types sorted by translated label. It is imported from `@etendosoftware/app-shell-core/components/ui/distinct-values-filter.jsx`. Do not use `@/components/ui/distinct-values-filter.jsx`: that is an older local copy without `heading` or `triggerTestId`.
  - **Filters live in the URL**: `?q=<text>` and `?accountType=<A|E|L|M|O|R>` (`chartOfAccountsFilters.js`; an unknown code means "all"). Compartir copies the page URL, so a shared link reproduces the filtered view, and Back restores it.
  - **A filter seeds the expansion.** When the search or the type changes, every folder leading to a match opens. The user can still collapse folders, including with "Contraer todo", while filtering. That expansion is temporary: it is never persisted, so clearing the filter, or leaving the window, restores the user's own persisted expansion (`restorePersistedExpanded`). A filter that is in the URL before the accounts have loaded seeds the expansion once they arrive. It only counts as seeded once the **full** dataset has loaded, not ListView's partial first page, so a shared link opens every matching branch.
  - **Ordenar** offers only **Código** and **Nombre** (decision Q2). The tree sorts siblings at every level, so folders keep their children; the default is code ascending. `elementLevel`, `accountType` and `active` are `sortable: false`. ListView's own default sort (`creationDate`) leaves the tree in code order.
  - **Imprimir** is unchanged: it prints the flat leaf report. With the YTD columns removed, they no longer appear in it either (decision Q4).
  - **Nueva subcuenta** is ListView's New button. `decisions.json` sets `hideCreate: false` and `customComponents.newRecordComponent: "NewSubAccountCreateModal"`, and the label comes from `windows."Chart of Accounts".newLabel` in the locales. The generated page mounts the wrapper with only `token`/`apiBaseUrl`/`windowName`/`onClose`, so `NewSubAccountCreateModal.jsx` reads the selected row and the already-loaded accounts from the window-local store. After a save it calls `notifySaved()`, and the tree refetches. The detail page's kebab "New Sub-account" (`menuActions.newSubAccount`) is unchanged.
  - **Shared state.** The slot, the create modal and the tree are siblings inside a generated page. They share `chartOfAccountsTreeStore.js` (`useSyncExternalStore`), which holds the expanded set (persisted to `localStorage`), the folder ids currently shown, the accounts, the selected row and a `savedGeneration` counter. The selection is cleared when the tree unmounts, so coming back from a record starts with no row selected.
- **Rows use the shared table primitives (ETP-5593).** The rows and the header are `components/ui/table` (`Table`/`TableRow`/`TableCell`, the same primitives `DataTable` uses), so hover, selected (`data-state="selected"`) and borders match every other grid. Folder rows expand with the shared `RowExpandToggle` (`orientation="horizontal"`: a right chevron that turns down), the same circular outline button the line panels use. Codes use the `font-code` family (Space Mono, core `tailwind-preset.js`). Folder codes are semibold and leaf codes regular. The status column header reads **Estado** (`accountTreeFilterActive`), not "Activo" (decision Q3). A quiet background refetch, after a save or a status toggle, shows a `ListProgressBar` above the tree. The first load and Actualizar keep the blocking skeleton (ETP-5387).

## Reactive behavior and dependencies
- There is no visible parent/child interaction because the window only exposes the `account` entity.
- `Parent Account` is the only cross-record dependency in the form. It is rendered as a search-based foreign-key field, so users can link an account to another account, but no catalog preload, hierarchy browser, or auto-filtering behavior is visible in the current generated assets. In the runtime custom subaccount-creation modal (`artifacts/chart-of-accounts/custom/NewAccountModal.jsx`), the parent selector is a searchable combobox (`AccountBadgeSelect`) rather than a plain list, and Account Type now defaults from the selected parent/sibling account's existing type instead of always defaulting to Expense.
- Debit, credit, and balance appear only in the table and are read-only in the contract, so the current surface behaves as account setup plus financial review rather than as a balance-editing screen.
- No dependent selectors, status-driven actions, totals, discounts, tax reactions, or line-level recalculations are visible in the current evidence.
- New subaccount creation is handled by the custom modal. The action is always available; when a branch or account row is selected, the modal defaults the parent selector from that row, and otherwise it opens with no parent selected.
- The 4-digit suffix field in the new-subaccount modal shows the **next available suffix** (highest existing sibling under the selected parent prefix, plus 1, clamped at `9999`) as its placeholder (e.g. `0005` when `20000001..20000004` already exist), computed client-side from the already-loaded account list; falls back to the generic `0000` placeholder when nothing exists yet under the prefix. Purely a hint — does not pre-fill or validate the field.
- Submitting a duplicate 8-digit code (one that already exists for the client) is rejected by `ChartOfAccountsHandler` with a specific `"Account <code> already exists."` message, translated and shown as a toast — not the generic "Could not create sub-account" fallback, which is now reserved for genuinely unexpected save failures.
- Account Type values are rendered from AD list translations extracted from `AD_REF_LIST_TRL`, so raw AD values (`A`, `E`, `L`, `M`, `O`, `R`) display consistently in English and Spanish.
- **Element Level column (ETP-5399):** the tree grid shows a dedicated `Element Level` column (`Heading`/`Account`/`Breakdown`/`Subaccount`), positioned between Name and Account Type, matching Etendo Classic's account list. It reads `item.elementLevel` — the same `C_ElementValue.ElementLevel` value already injected onto every row (real leaf or virtual folder) by `ChartOfAccountsHandler.injectHierarchyFields` for the hierarchy/insertion logic above, now also surfaced to the user. Label mapping lives in `ELEMENT_LEVEL_UI_KEYS`/`elementLevelLabel` (`artifacts/chart-of-accounts/custom/accountTypeLabels.js`), mirroring the pre-existing `ACCOUNT_TYPE_UI_KEYS` pattern. `decisions.json` still marks the raw `elementLevel` entity field as `discarded` — that only governs the generic generated form/contract, not this custom tree render, which renders it directly from the handler-injected row data.
- Parent-like posting subaccounts with an 8-digit code ending in `0000` are protected. The form renders Code, Name, Description, and Account Type as read-only for existing protected records (`readOnlyLogic: "@ProtectedParentLikeSubaccount@='Y'"` in `decisions.json`, backed by `ChartOfAccountsHandler.isProtectedParentLikeSubaccount`), and the backend rejects creating or modifying those codes. These leaves are technically `issummary='N'` (real DB leaves) but still function as placeholders under their breakdown group — the tree view marks them with a lock icon (`account-tree-locked-<id>`) even though they remain clickable for read-only viewing. Real subaccounts (e.g. `20000001`) are unaffected and stay fully editable.
- The tree's full hierarchy comes from a per-leaf `ancestors` array (root-to-leaf, `{value, name, elementLevel}`) injected by `ChartOfAccountsHandler`, built by walking the client's `AD_TreeNode`/`AD_Tree` ("`<ClientName> Element Value`", `ad_table_id = 188`). `elementLevel` mirrors `C_ElementValue.ElementLevel` (`E` Heading, `C` Account, `D` Breakdown, `S` Subaccount). The legacy 2-level `parentCode4`/`parentCode4Name` fields are still injected for backward compatibility with `NewAccountModal`'s parent selector and as a fallback if `ancestors` is ever absent.
- **New sub-account parent/prefix resolution is `ElementLevel`-based, not string-shape-based (ETP-5399).** The original logic derived a new sub-account's parent prefix by treating any 4-character code as "the summary account". That silently mis-resolved letter-suffixed `430A`, which is an Account-level (`C`) node, instead of drilling into its actual Breakdown-level (`D`) children: `4300A`, `4304A`, and `4309A`. The fix keys off `C_ElementValue.ElementLevel` instead of the `Value` string's shape:
  - **Backend:** `ChartOfAccountsHandler`/`ChartOfAccountsTreeMath` (com.etendoerp.go) compute `insertionChildren` per leaf/node — the real, structural insertion candidate(s) for a new subaccount under it — and inject that field into the relevant NEO responses. A Breakdown (`D`) node is always the correct structural parent depth for insertion, regardless of whether its identity is numeric (`2000`) or letter-suffixed (`4300A`); a Subaccount (`S`) leaf reuses its parent's already-resolved `insertionChildren`; any other level drills into real children, surfacing all of them as candidates when there is more than one (never guessing a single answer among real siblings).
  - **Structural identity and posting prefix are deliberately separate.** Selecting `4300A` preserves that exact value as the structural parent identity shown by the selector and carried in `insertionChildren`. The locked posting prefix supplied to the code field is derived independently from its first four numeric characters, `4300`. A suffix such as `1000` therefore produces the valid final 8-digit account code `43001000`; the UI and backend must never concatenate `4300A` with the suffix or replace the structural parent identity with `4300`.
  - **Frontend:** `artifacts/chart-of-accounts/custom/NewAccountModal.jsx`'s `resolveInsertionCandidates()` mirrors the structural algorithm client-side over the already-loaded local tree node, so a single confident candidate becomes the modal's default parent, while zero or multiple candidates (genuine ambiguity — e.g. Account-level `430A` fanning out into several real Breakdown children) leave the parent selector empty for the user to pick manually rather than guessing. `derivePostingPrefix()` then converts the selected structural parent code to the separate numeric code prefix. `artifacts/chart-of-accounts/custom/AccountTreeView.jsx` also resolves the selected row against the tree's **unfiltered** `indexById` map (`currentRecordForModal`) before handing it to the modal, since an active text/type filter clones virtual folder nodes with a pruned `children` array that would otherwise starve this resolution of a node's real children. The Account-Type sibling-match in `deriveDefaultAccountType()` likewise now prefers each candidate leaf's own `insertionChildren[0].value` over `parentCode4` when matching siblings under a resolved structural parent.
  - **`parentCode4`/`parentCode4Name` are now a fallback only** — used solely when a caller hands a bare `{searchKey, summaryLevel}` shape with no `elementLevel`/`children` at all (an older API response, a legacy tree shape, or a minimal test fixture predating this field). Even in that fallback path, the numeric-only heuristic (`summaryLevel === 'Y' && code.length === 4 && /^\d+$/.test(code)`) no longer matches a letter-suffixed 4-character code, so the original bug stays closed even without structural data.
- **Full-dataset self-fetch (bug fix):** `ListView.jsx` only ever hands the tree one paginated page of leaves (`hook.items`, capped at `BATCH_SIZE`) and does not forward `hasMore`/`loadMore` to the `Table` it renders — a scroll-triggered "load more" also can't work for a collapsed-by-default tree, and a tree needs the complete leaf list upfront just to know which root headings exist. This previously made entire top-level roots (e.g. `PYG`, `O`) silently disappear whenever no leaf under them landed in the first page — confirmed live on a tenant with 659 leaf accounts across 4 roots, where only 2 roots ever rendered. `AccountTreeView` now fetches its own complete leaf dataset directly (`GET {apiBaseUrl}/elementValue?_startRow=0&_endRow=9999`, same pattern already used by `NewAccountModal`'s parent selector) on mount and again after every new sub-account is saved, and renders that instead of the paginated `data` prop once it resolves. While the fetch is in flight the first load shows the skeleton (see below), and later background refetches show a `ListProgressBar` above the tree (ETP-5593; this replaced the old toolbar spinner); on failure it falls back to the `data` prop and shows an error toast (`accountTreeFetchError`) instead of crashing or silently truncating the tree. When `apiBaseUrl` is not supplied (e.g. direct unit tests that only pass `data`), the component skips the self-fetch and renders `data` unchanged.
- **Initial loading skeleton, no partial-tree flash (ETP-5387):** the self-fetch above used to leave a visible gap — while the very first fetch was in flight, the component rendered the tree built from the partial `data` prop (only the roots that happened to have a leaf in ListView's first page) underneath the toolbar's "Cargando…" spinner, then replaced it with the full tree once the fetch resolved. That partial-tree-then-full-tree swap was itself a visible flash. The component now tracks `hasLoadedOnce` (whether any self-fetch attempt has ever *settled*, success or failure — set once in the effect's `finally`, never reset) and derives `showInitialSkeleton = !!apiBaseUrl && !hasLoadedOnce && isFetchingFull`. While that flag is true, `treeBody` renders a full-page `AccountTreeSkeleton` instead of any data-driven tree, so the partial `data` prop is never painted. The flag flips to `false` for good the moment the first attempt settles — including on failure, where the existing fallback-to-`data` + error-toast behavior takes over unchanged — so every later background refetch (after saving a new sub-account, or an active-toggle flip) only shows the toolbar's small spinner and never re-shows the full-page skeleton, even if that first attempt had failed. Gating on `hasLoadedOnce` rather than `fetchedData === null` is deliberate: the latter would flip back to `true` on a post-failure retry (since a failed fetch never sets `fetchedData`), wiping the already-visible fallback tree and re-showing the skeleton for what should be a quiet background retry.
- **Refresh button reloads the tree, with the same skeleton (ETP-5387 QA):** ListView's toolbar Refresh only reloads ListView's own paginated page (`hook.refresh()`), which this tree never renders — so pressing it used to change nothing and show no loading signal. ListView now also bumps a `userRefreshTrigger` counter that it forwards to the headerTable (only for the Refresh button — not for `onDataMutated` reloads nor for the host's `refreshTrigger` input prop). `AccountTreeView` reacts to a change of that value (the value it mounts with is a baseline, not a request) by refetching the full dataset behind the same blocking skeleton as the first load; background refetches after a save or an active toggle stay quiet. A failed refresh brings the previous tree back with the `accountTreeFetchError` toast. (The toolbar loading text `accountTreeLoadingFull` was removed in ETP-5593 together with the tree's own toolbar.)
- **Account Type is actually saved (ETP-5399 QA, finding #1):** creating a subaccount always stored Expense (`E`) whatever the user picked. The modal sent `accountType` correctly; NEO dropped it because the `ETGO_SF_FIELD` row for `C_ElementValue.AccountType` was closed (`ISINCLUDED=N`, `VISIBILITY=discarded`, `JAVA_QUALIFIER=accountType2`), so `NeoFieldFilter` stripped the value from POST (and PATCH) and the AD default applied. Root cause: the extractor joined `AD_Model_Object` on the callout without filtering by action, and core ships a stray `Action='P'` row for callout `SE_ElementValue_AccountSign` next to the real `C` one (reported as etendosoftware/etendo_core#1162) — so AD field 510 came out twice, the copy was named `accountType2` and curated `discarded`, and push-to-neo (last write wins on the single row per column) let it close the real field. Fixed in `schema_forge_core`: the extractor now joins only `Action = 'C'`, and push-to-neo / the offline delta coalesce any fields sharing an `(entity, column)` so the most-exposed visibility wins. `accountType2` is gone from `decisions.json`, and the row in `com.etendoerp.go`'s `ETGO_SF_FIELD.xml` is back to `ISINCLUDED=Y`, `VISIBILITY=editable`, `JAVA_QUALIFIER=accountType`. The list never showed the problem because `ChartOfAccountsHandler` reads accounts with its own SQL, bypassing the field filter.
- **New sub-account modal UX (ETP-5399 QA):** once the user picks an Account Type, changing the parent no longer overwrites it with the derived default (the derivation still runs while the type is untouched, and resets on every open). The code field renders the locked prefix and the 4-digit suffix as one bordered control (`account-code-control`) with monospace digits and a foreground-coloured prefix, replacing the pale prefix with an invisible border. The dialog is `max-w-xl`, parent names carry a `title` tooltip in the selector list and on the selected value, and the selector opens its popover with `modal` so the option list scrolls inside the dialog (without it, the dialog's scroll lock swallowed wheel events on the portalled list). `AccountBadgeSelect`'s `modal` prop defaults to `false`, so the General Ledger Configuration tabs are unchanged.
- **Element Level / Account Type columns line up on every row (ETP-5399 QA):** folder rows have no active toggle, and without a cell in its place the flex-1 name cell grew and pushed Element Level and Account Type to the right, so Epígrafe/Cuenta/Desglose looked right-aligned while Subcuenta did not. Folder rows now render an empty `w-10` placeholder (`account-tree-active-placeholder-<id>`).
- **Tree-native filter (bug fix):** The generic "Filtros" advanced-filter builder is designed to trigger backend-paginated re-fetches, which doesn't fit this component — it already self-fetches and holds the complete dataset in memory, so a backend-filtered response never actually reaches the rendered tree. `AccountTreeView` marks its columns `filterable: false` (so the generic builder's field picker no longer lists `searchKey`/`name`/`elementLevel`/`accountType`/`active` as choosable fields — the Filtros button itself remains, it simply has nothing tree-specific left to filter by) and instead filters, from the search box and the account-type picker in the list toolbar (ETP-5593; URL params `q` / `accountType`), the already-materialized tree in JS via `filterTree`. A text match on a virtual folder's displayed code or name keeps that folder and its relevant descendant leaves; account-type filtering is still applied to those leaves, so unrelated leaf types are removed. This supports letter-suffixed folder codes such as `430A`, auto-expands matching ancestors, and hides branches with no matching descendant.

## Gap assessment
- A chart-of-accounts screen often carries stricter accounting semantics such as deleting accounts with activity or account-type-specific behavior. Those rules are not visible in the current contract or generated UI, so they remain gaps or open ambiguities.
- The presence of a `Parent Account` field suggests hierarchical setup, but the current evidence does not show how hierarchy depth, rollups, or parent eligibility are enforced.
- The custom subaccount-creation modal (`NewAccountModal.jsx`) renders `Account Type` as a required dropdown sourced from `ACCOUNT_TYPE_UI_KEYS`, defaulting from the selected parent/sibling account's existing type (falling back to Expense (`E`), the AD column default, when no parent/sibling type can be resolved).
- The balance columns show useful review data, but no evidence here explains whether they are point-in-time totals, ledger-derived live balances, period-sensitive balances, or mock/demo placeholders outside real backend data.
