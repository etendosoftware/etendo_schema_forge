# MCP Evaluation

Everything about measuring and improving the **Etendo GO MCP server** as an agent-facing product:
the benchmark against a reference vendor MCP (Holded), the IMP-* improvement backlog, the MARI
readiness index, and one working file per improvement.

Refresh the measurement with the `/mcp-comparison` skill. **Never** write a status anywhere except
the registry.

## What the `imps/` files are for

A registry row is one line: status, points, an evidence pointer. That is the right size for a
scoreboard and the wrong size for actually fixing something. The run reports, in turn, record what
was *observed* — not what the code turned out to be.

An `imps/IMP-n.md` file holds the third thing: **the investigation**. Where the responsible code
actually lives, what the DB actually contains, which of the competing hypotheses survived contact
with the data, and what the fix therefore has to touch. It is written **while the item is worked**,
so it is empty for every item nobody has opened yet — that is expected, not a gap.

The distinction that matters: a run report may say *"0 of 157 fields carry `visibility`"*. That is an
observation, and it is compatible with several very different root causes. The IMP file is where
those causes get discriminated with evidence, and where a wrong first guess gets recorded as wrong
rather than quietly replaced.

**Conventions:**

- Naming: `imps/IMP-<n>.md`, zero-padding not used (`IMP-11.md`).
- Numbers are permanent. Never renumber, never recycle — the registry, the run reports and the base
  report all cross-reference them.
- The file may contradict an earlier diagnosis. When it does, say so explicitly and keep the
  superseded claim visible with the evidence that killed it. Silent overwrites are how the old
  five-places-status problem started.
- **Status still lives only in the registry.** An IMP file describes the work; it never declares the
  item resolved.

| IMP-23 | [`imps/IMP-23.md`](imps/IMP-23.md) | **Both options implemented** 2026-08-10 — A deployed and verified live, B committed and awaiting a deploy, so the registry row is still ⚠️ at 0 / 5. **Investigated and half-implemented** first; the registry row moves ⏳ → ⚠️ and the score stays 0 / 5, because option A does not make the batch atomic. §1 reads the mechanism out of the code instead of inferring it: `BatchService` is **correct** — the unconditional `commitAndClose()` is four calls below it, in core's `DefaultJsonDataService#update`, so every op commits itself and the batch's own rollback finds an empty session. §2 checked the cheap fix before any code was written and **it does not exist** (no parameter on `add()`; `setDoRollback` is read only by `DalThreadHandler` at thread end; `TriggerHandler.disable()` makes `commitAndClose` *throw*), which is what makes real atomicity a core fork — option B, deferred **but kept under this same row rather than filed as a new IMP** (§5.1 corrects the file's own first recommendation: B is the first clause of IMP-23's title, so filing it separately would force a quota re-base and cost ~3 MARI points for identical code), so that a P1 agent-ergonomics fix does not wait on it and the shipped React invoice-scan ingest stays out of the blast radius. **Two findings the registry cell did not have:** the REST `POST /sws/neo/batch` shares `executeBatch` verbatim and has been non-atomic since it shipped, so this was never MCP-only; and the surviving ids were **already in memory** in `opResults` and `failureBody` threw them away — which is exactly why orphan `1000017` survived five days, the agent having been told `committed:false` and given no reason to look. Option A stops discarding them (`persisted`, `atomic:false`, `hint`), emitted even when empty so that “nothing survived” cannot be mistaken for “we are not saying”. Its most instructive part is the tests: they had to be **inverted**, not updated — `verify(obDal, never()).commitAndClose()` passed because the mocked CRUD seam meant nothing downstream ran, and `ToolRegistryTest` required the description to “mention atomic transaction”, which it did while being false. **Verified live the same day** (§9): the C10 re-run names the survivor and the recovery loop was executed, not asserted — `neo_get` confirmed the orphan, `neo_delete` removed it with the id the failure body supplied, and a sweep found nothing left. Both hint branches are confirmed, the empty one by accident and it is the better probe. §9.3 records a limit no code change reaches: the MCP client caches tool descriptions at session start, so an agent already connected keeps reading the retired atomicity promise — an argument for fixing the response body rather than the description alone. §9.4 notes a secondary finding left unregistered: the same tool returns a clean 400 for an over-length value but a 500 with a raw Postgres row dump for an omitted required FK. **Option B then followed the same day** (§11, commit `7159376c`): `NeoBatchJsonDataService` forks core's `update()` minus the two lines that end the transaction, a `ThreadLocal` in `BatchService` marks that a caller owns it, and **one line** at `NeoCrudHandler:237` feeds the whole create path — far cheaper than §4 estimated, because that injection point already fanned out by parameter. What is worth reading §11 for is not the fork but the three things that pushed back: making the subclass a CDI bean was **mandatory**, since core injects into it and `doPreAction` dereferences the injection, and it is only safe because Weld's static lookup matches the bean class *exactly*; the ownership flag had to live outside the subclass, because loading it runs core's Weld-dependent **static initializer**; and the failure body had to change **direction**, since after B a blanket `atomic:false` would be the mirror image of the original bug — so survivors are now detected generically, by Hibernate `Session` identity, which is also the only part of B a mocked test can see. The batch is atomic but **not hermetic** (`ProcessInvoiceUtil#process` commits by design — exactly what the new `atomic:false` reports), and the React invoice-scan ingest **silently gains atomicity** through the shared `executeBatch`. The ⚠️ → ✅ flip waits on a live probe and a re-measure |
