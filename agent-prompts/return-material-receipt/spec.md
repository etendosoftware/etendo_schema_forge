Customer returns (Return Material Receipt): goods a customer sends back against a completed goods shipment, optionally refunded with a factura rectificativa (corrective sales invoice). Entity `returnMaterialReceipt` is the header, `returnMaterialReceiptLine` the lines. Two ways to create one. FAST PATH, from one shipment: etendo_action `createReturn` on the completed goods shipment (spec goods-shipment, entity goodsShipment) creates the return already linked to it, in DRAFT; omit `lines` to return everything still returnable, or send {lines:[{lineId, returnQuantity}]} to return exactly those (the answer lists each created line with its sourceLineId). THE UI's FLOW, which also lets one return take lines from several shipments of the same customer, in this order: (1) create the header with etendo_create on `returnMaterialReceipt`: businessPartner and partnerAddress are the fields to send — warehouse, movementDate, document type and currency are defaulted — and etendo_schema with view:"create" (or etendo_defaults) is the authority on what a create needs; (2) etendo_action `availableShipments` with {businessPartner} and id "_" lists the customer's completed shipments that still have quantity to return; (3) `availableShipmentLines` with {shipmentId} and id "_" lists that shipment's returnable lines; (4) `importShipmentLines` on the new header id with {lines:[{sourceLineId, returnQuantity}]} adds the return lines; (5) confirm the return with the DocAction button (action documentAction, docAction CO) — confirming does NOT create the factura rectificativa, the corrective invoice that refunds the return; that is a SEPARATE call made after the confirmation; (6) `rectifiableInvoices` on the header id lists the invoices it can rectify and hasReturnInvoice (true when the return already has a factura rectificativa); (7) `createReturnInvoice` on the header id with {originInvoices:[...]} (optional: by default the invoice the returned shipment lines were billed on) creates the factura rectificativa, links it to the invoices it rectifies and confirms it, leaving it COMPLETED. It does NOT refuse a second call: a return that already has one gets another, so check hasReturnInvoice first; the answer lists the ones it had before in previousReturnInvoices. It answers {id, documentNo, documentStatus, documentType, isSalesTransaction, grandTotalAmount, totalLines (net), linkedReturnId, returnDocumentNo, rectifiedInvoices, previousReturnInvoices}; the amounts are negative because it refunds. A product with no price source (not on the invoice being rectified, nor on its order line, nor in the price list) answers 422 returnInvoiceWithoutAmount (naming the products) and creates nothing; a product deliberately invoiced at 0 is refunded at 0 and is not refused; a return whose shipment was never invoiced answers 400 (no invoice to rectify). The classic invoice buttons of the window (GenerateTo, Invoicefromshipment) are not agent paths: they point at createReturnInvoice. Return lines exist only by import: there is no manual line entry with a product. A return can never take more than what is still returnable of a shipment line: what other non-voided returns of that line hold, drafts included, is already taken. Asking for more answers 422 returnQuantityExceedsAvailable (naming the product, the requested and the available quantity) and creates nothing, including when the quantity of an existing return line is edited above it. Reading a return: documentAction on the record is the next default action of the document (what its Process button would run); "--" means none, the document is in a final state. invoiceStatus is the percentage of the return already refunded by invoice; hasReturnInvoice and returnInvoices say whether it already has a factura rectificativa. What can be done NOW: before offering an action on a return call etendo_schema with view:"actions" and id = the return id; each action carries availableNow (true or false) and, when false, unavailableReason, and documentAction carries availableValuesNow. Unavailable actions stay listed so you can explain why to the user. This is advice, not a lock: the server still validates every call. createReturnInvoice applies to a completed return that has no factura rectificativa yet; its availableNow says so, and a second call would NOT be refused. A completed return cannot be reactivated or voided through MCP (documentAction offers CO only, to complete a draft). Posting a just-completed document (action post) can answer 409 costNotCalculated with retryAfterSeconds 30: Etendo calculates cost in the background about every 30 seconds, nothing was posted, so wait and repeat the same post. If it answers costCalculationStalled instead (retryable false, no retryAfterSeconds), costing is stuck, not slow: do not retry, tell the user an administrator must check the Costing Background process and the transactions waiting for cost. Book and unbook the document with the post and unpost actions (they appear in the actions view with availableNow); the AD Posted button is hidden and must not be used. post applies to a completed document that is not posted, unpost to a completed one that is. etendo_schema with view:"actions" returns each action's parameters. Document tools. Several return receipts at once (up to 50, one result each, not atomic): etendo_action_batch (e.g. complete them all). Attachments: etendo_request_attachment_upload, etendo_list_attachments, etendo_delete_attachment; do not pass main:true here, the main file is the document's own PDF. PDF: etendo_get_document_pdf returns the stored PDF; a draft has none, and this preview stores nothing, so on no_pdf or pdf_stale the user must send the document by email from the application. Email: etendo_send_document_email (preview:true first); the first send is done from the application.
