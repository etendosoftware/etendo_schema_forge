SEPA remittances (Etendo table REM_Remittance): a batch of customer collections (SEPA CORE direct debit) or vendor payments (SEPA credit transfer) that the company sends to its bank in one file. Only available when the account has the sepa-remittances feature enabled; otherwise every call answers 403 feature_disabled. The `remittance` entity is the header: create it with name (max 60 characters), financialAccount (only a Bank account with a valid IBAN that has the SEPA remittance payment methods, which Bank accounts get automatically when they are created with the feature on), remittanceType (its name says whether it is a collection or a payment remittance; only the types linked to the chosen account are accepted) and dueDate (the date the bank charges or credits the remittance, never in the past). documentNo, transactionDate and the document type are assigned by the server, and remittanceStatus (PE Pending, PR Processed i.e. pending dispatch, SB Sent to bank, CT/PT Collected/Paid, CP/PP partially, AN Voided) is set by the remittance processes and never written. A confirmed remittance cannot be edited. To add lines, use the header actions (etendo_action): `availableDueItems` (body `{ search, page, pageSize }`) lists the open due items the remittance can take (the ones already in it come back marked alreadyInRemittance, with their lineAmount and lineIds), and `syncDueItems` (body `{ items: [{ id, amount }], remove: [id] }`, ids are due-item ids) adds or updates and removes them in one transaction; an amount must be greater than 0 and at most the due item's outstanding amount. The `lines` entity cannot be created directly (POST answers 405): each line is one due item (paymentScheduleDetail) of the remittance, with read-only invoice, business partner and due date fields; while the remittance is pending, a line's `amount` can be updated (same limit) and a line can be deleted. The Classic remittance processes (select payments, process remittance, create remittance file) are not exposed; use these remittance actions instead (etendo_action): `fileReadiness` (read) lists what still prevents generating the SEPA file (`problems`, each with a localized `message`, grouped by organization, bank account and line) and summarizes the remittance (invoices, total, due date); `confirm` (body `{ fieldValues: { grouping: 'P' | 'GGPD' } }`, P no grouping, GGPD grouped by business partner and due date) is atomic: it processes the remittance and creates its payments as Remitted WITHOUT settling them (the invoices stay unpaid and the remittance ends PR, pending dispatch), generates the SEPA file (pain.008 for collections, pain.001 for payments), stores it as the remittance's main attachment and returns `status`, `attachmentId`, `fileName` and `downloadUrl`; if anything fails nothing is kept. After confirming, `reactivate` (no parameters) undoes it while the remittance is PR or SB. `markSent` (no parameters) records that the file was sent to the bank (PR to SB): informational only, nothing is settled. `markCollected` (no parameters, from PR or SB) settles every payment on the remittance due date (the bank transaction and the paid invoices; the remittance ends Collected, or Paid for a payment remittance); it is all or nothing and afterwards the remittance cannot be reactivated and the only way back for a collection is to register returns, below. Ask the user before marking a remittance collected. `generateFile` regenerates the file of a confirmed remittance as a new main attachment (the previous files are kept) with the same response; it is refused once a line was returned (the file would still list it). When the bank did not collect an invoice of a collected remittance (only after `markCollected`), register a return by hand with `returnState` (read: per line `state`, `returnable`, `reasonCode`, `returnDate`, and `paymentLineIds`, the lines that share a payment) and `returnLines` (body `{ fieldValues: { lineIds: [lineId], returnDate: 'yyyy-MM-dd' } }`, date optional, default today, never in the future; a payment shared by several lines must be returned with all of them): it reverses the settlement and its bank transaction, voids the line's payment so the invoice due is pending again, and moves the remittance to partially collected (CP); it is all or nothing, only for a collection remittance, and refused for lines whose settlement is posted or reconciled (the refusal lists `problems` per line). Ask the user before returning. Run `fileReadiness` before `confirm`, fix or report its problems, and ask the user before confirming.
